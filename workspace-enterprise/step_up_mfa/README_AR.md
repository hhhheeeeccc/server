# التحقق الإضافي MFA للعمليات الحساسة

## الربط والتفعيل

تسجل حزمة `step_up_mfa` وسيط HTTP من `enterprise/main.go` داخل `init()`،
دون تعديل مسارات `mattermost/server/`. لا تتطلب مفتاح تشغيل عامًا: كل عملية
تُحمى بحسب خيارها المحفوظ في سياسة PostgreSQL المشتركة، بعد تفعيل MFA
الاعتيادي على النظام وحساب منفذ العملية. تتبع الخيارات بذلك طريقة المشروع
المرجعي، مع بقاء التخزين منفصلًا لأن حقول إعداداته ليست في الكور الحالي.
الخيارات مفعلة افتراضيًا في التثبيت الجديد، ويمكن ضبطها من صفحة الإدارة.
يمكن ضبط `WORKSPACE_STEP_UP_MFA_GRACE_MINUTES` من 0 إلى 1440 عند إنشاء الصف،
والافتراضي 30 دقيقة كما في المشروع المرجعي. يمكن تعديله لاحقًا من الواجهة.
تظهر سياسة العمليات ضمن صفحة الإدارة `authentication/mfa` أسفل إعدادات المصادقة
الثنائية الأصلية؛ العنوان القديم `authentication/step_up_mfa` يحوّل إليها. يمكن
لصاحب صلاحية قراءة إعدادات MFA الاطلاع عليها، ولصاحب صلاحية الكتابة تغييرها.
يستخدم المسؤول زر «حفظ» الرئيسي في صفحة MFA للخيارات كلها. يحفظ تفعيل MFA
وفرضه عبر إعدادات Mattermost الأصلية، ثم يحفظ خيارات العمليات الحساسة عبر
API سياسة Enterprise في PostgreSQL. إذا فشل حفظ إعدادات Mattermost لا يبدأ
حفظ السياسة، وإذا فشل حفظ السياسة تبقى الصفحة في حالة تحتاج إعادة المحاولة.
يتطلب حفظها رمز TOTP جديدًا حتى لو كانت الجلسة ضمن فترة السماح.
تتطلب واجهة الحفظ جميع حقول السياسة والإصدار الحالي في كل طلب؛ يُرفض JSON
الجزئي أو قيمة `null` لأي حقل إلزامي أو `grace_minutes` خارج 0–1440 بحالة
`400` قبل التخزين، فلا تتحول الحقول المحذوفة إلى `false` من دون قصد.
طلب السياسة الذي يتجاوز 4 KiB يرد `413` حتى إذا كانت الزيادة فراغات بعد
كائن JSON صحيح؛ يحتفظ المحلل بخطأ حد القراءة الأصلي ولا يغيّر الصف المحفوظ.
أثبت اختبار API `TestPolicyAPIRejectsOversizedUpdateWithoutChangingSavedPolicy`
هذا السلوك، ونجح `go test ./step_up_mfa -count=1` و`go vet ./step_up_mfa`
في 1 أكتوبر 2026.
لا يوجد حقل `enabled` عام يتحكم في Step-up MFA. يحتفظ رد API بالحقل مؤقتًا
لتوافق واجهات الويب القديمة، ويعرض حالة MFA الاعتيادي؛ يُقبل الحقل في طلب
قديم دون استعماله لتفعيل الحماية أو تعطيلها. الواجهة الجديدة لا تعرضه.
يمكن تعطيل مطالبة عملية بعينها عند إنشاء السياسة أول مرة بضبط أحد المتغيرات التالية على
`false`: `WORKSPACE_STEP_UP_MFA_TEAM_DELETION`،
`WORKSPACE_STEP_UP_MFA_USER_DELETION` (يشمل تعطيل مستخدم آخر)،
`WORKSPACE_STEP_UP_MFA_USER_PASSWORD_CHANGE`،
`WORKSPACE_STEP_UP_MFA_USER_MFA_REMOVAL`، و
`WORKSPACE_STEP_UP_MFA_CONFIG_DISABLE`. جميعها مفعلة افتراضيًا عند تفعيل
MFA الاعتيادي. تُستعمل هذه المتغيرات لإنشاء صف السياسة في PostgreSQL فقط؛
بعد ذلك تصبح القاعدة المصدر المشترك، ولا يغير تبديل المتغيرات سياسة محفوظة.
قراءة السياسة وحفظها محدودتان بخمس ثوانٍ أو بمهلة الطلب الأقصر. إذا تعذر
جلب السياسة خلال المهلة، يرد الوسيط `503` ولا يمرر العملية الحساسة إلى
المعالج الأصلي. أثبت اختبار نفاد تجمع اتصالات PostgreSQL رد الرفض وانتهاء
محاولة الحفظ بمهلة، دون انتظار اتصال إلى أجل غير محدد.
القيمة غير المعروفة تُبقي الحماية مفعلة عند الإنشاء. عند ترقية صف قديم فقط،
يُقرأ `WORKSPACE_STEP_UP_MFA_ENABLED` مرة واحدة: إذا لم يكن `true` تُنقل
الخيارات الخمسة إلى `false` حتى لا تتحول حماية كانت متوقفة إلى مطالبة مفاجئة؛
إذا كان `true` تبقى الخيارات القديمة كما هي. بعد ذلك لا يؤثر المتغير في
السياسة، وتقرأ كل عقدة الصف المشترك دون إعادة تشغيل عند تعديل الخيارات.
لا يعمل الوسيط دون رخصة Enterprise أو عندما يكون MFA العام معطلًا أو غير مفعل
على حساب منفذ العملية. لا يطلب الرمز من الجلسات المحلية للخادم.

يرسل العميل رمز TOTP في ترويسة `X-MFA-Code`. تستعمل الحزمة
`App.CheckUserMfa` للتحقق، ثم تحفظ وقت نجاح التحقق في خصائص الجلسة على الخادم
وتبطل كاش الجلسات عبر العقد. لا تحفظ الرمز. إذا كان وقت السماح صفرًا، تحتاج
كل عملية محمية إلى رمز جديد؛ وإن كان أكبر، تقبل الجلسة نفسها ضمن المدة.
تعرض واجهة الويب نافذة الرمز عند تلقي `ent.step_up_mfa.required`، ثم تعيد
الطلب المحمي وحده بالترويسة. عند رفض الرمز تعطي محاولتين إضافيتين، وعند
الإلغاء لا تعيد الطلب. لا تضاف الترويسة إلى الإعدادات العامة لعميل HTTP.

## العمليات المحمية

- حذف فريق أو مستخدم، مع مراعاة صلاحية المنفذ قبل طلب الرمز. يشمل حذف
  المستخدم من يملك صلاحية `edit_other_users` عبر دور مدير المستخدمين، وليس
  مسؤولي النظام وحدهم؛ حذف المستخدم لنفسه يبقى تحت ضوابط المسار الأصلي.
- تعطيل مستخدم آخر أو تغيير كلمة مروره أو تعطيل MFA له، بحسب جسم الطلب
  وصلاحية المنفذ. تغييرات المستخدم لنفسه تمر إلى ضوابط المسار الأصلي.
  جلسات OAuth لا تُطالب برمز إضافي عند طلب تعطيل MFA لمستخدم آخر؛ يرفضها
  المسار الأصلي بصلاحياته قبل تنفيذ التغيير، كما في المشروع المرجعي.
- تعطيل MFA العام عبر `PUT /api/v4/config` أو
  `PUT /api/v4/config/patch` لمن يملك صلاحية إعدادات MFA.

تظل المصادقة والصلاحيات وتنفيذ العملية بيد المسارات الأصلية؛ يفحص الوسيط
جسم الطلب بحد 1 MiB ويعيده كما كان قبل تسليمه إلى المعالج الأصلي. عند غياب
الرمز يرد `403` بمعرف `ent.step_up_mfa.required`، وعند الرمز الخاطئ يعيد
خطأ `CheckUserMfa` الأصلي.

## التحقق والحدود

نجح `go test ./step_up_mfa -count=1`: المسارات المحددة، رفض حذف فريق دون رمز
أو برمز خاطئ، النجاح برمز صحيح، صلاحية الجلسة ضمن فترة السماح، منع تعطيل
مستخدم وMFA العام، وعدم فرض الميزة دون رخصة. اختُبر أيضًا مدير مستخدمين
يحذف حسابًا آخر: يُرفض دون رمز، ثم ينجح برمز صحيح. شملت اختبارات السياسة
صلاحيات القراءة، والرمز الجديد عند الحفظ، وتعارض الإصدار `409`، وتطبيق التغيير دون
إعادة تشغيل، ورؤية مثيل تطبيق ثانٍ للتغيير عبر القاعدة المشتركة. عند فقدان
صف السياسة يرد طلب القراءة والعملية الحساسة `503` بدل تجاوز الحماية.
ينطبق الرفض نفسه على سياسة مخزنة `null` أو ناقصة الحقول أو تحتوي قيمة
`null` لحقل إلزامي؛ لا تُحوَّل الحقول الغائبة إلى خيارات معطلة.
اختُبر رفض طلب سياسة جزئي عبر API بحالة `400` مع بقاء الصف المحفوظ، واختُبرت
حالات `null` وفترة السماح خارج المجال والإصدار السالب والحقول غير المعروفة
وJSON المتعدد مباشرة في محلل الطلب. يمنع Mattermost إعادة استعمال رمز TOTP؛
لذلك لا يعيد اختبار API إرسال الرمز نفسه لطلبات متعددة.
نجحت اختبارات عميل HTTP لحقن الرمز في الطلب المعاد فقط، والرمز الخاطئ
والإلغاء، واختبارات نافذة الإدخال وصفحة الإدارة وعميل السياسة، مع فحص
TypeScript. تعرض الصفحة تعارض الإصدار وتُبقي التعديلات المحلية للمراجعة.
يثبت اختبار API أن جلسة OAuth التي تطلب إزالة MFA لمستخدم آخر تتلقى خطأ
الصلاحيات الأصلي `api.context.permissions.app_error` بدل مطالبة Step-up.

في 17 أكتوبر 2026 نجح أيضًا اختبار Chromium 152 بالواجهة المبنية الكاملة
وخادم الكور وقاعدة PostgreSQL مؤقتين خلف HTTPS محلي. من صفحة تفاصيل المستخدم
العربية اختُبر إلغاء التعطيل وبقاء الحساب نشطًا، ثم رفض رمز خاطئ وقبول TOTP
صحيح وإعادة طلب العملية الأصلية. أثبت تعطيل مستخدم ثانٍ فترة السماح للجلسة
نفسها، بينما طالبت جلسة مستقلة للمسؤول نفسه برمز جديد. لم تنتقل ترويسة الرمز
إلى طلبات أخرى. اختُبر زر «حفظ» الرئيسي في صفحة MFA: يتطلب رمزًا جديدًا
خلال فترة السماح، ويحفظ السياسة بإصدار جديد ويعرضها بعد إعادة تحميل الصفحة.
تحقق اختبار Go من حالة الحسابات وخصائص الجلستين والسياسة المحفوظة بعد
تفاعلات المتصفح. لم يحتج تنفيذ الخدمة أو الواجهة إلى تعديل لاجتياز الحالات.
المشغل والدليل في [deployment/step_up_mfa](../deployment/step_up_mfa/README_AR.md)
و[تقرير المتصفح](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-17/step-up-mfa-browser/README_AR.md).

للاستعادة عند فقدان صف السياسة، أوقف العمليات الحساسة مؤقتًا، وافحص اتصال
PostgreSQL ثم أعد إنشاء الصف من نسخة احتياطية أو أعد تشغيل عقدة Enterprise
لتنشئه من قيم البيئة الأولية. راجع السياسة في صفحة الإدارة قبل استئناف العمل؛
حذف الصف عمدًا يعيد الإعدادات الأولية ولا يستعيد آخر إصدار محفوظ.

هذه طبقة حماية لمسارات HTTP المذكورة، وليست بعد تكافؤًا كاملًا مع المشروع
المرجعي: لا توجد حقول السياسة في `model.Config` الحالي. العمليات الداخلية التي
لا تمر بموجّه HTTP لا يعترضها الوسيط. نجح المتصفح المحلي بجلستين، وتبقى
تجربة جهازين فعليين وتعدد العقد والوكيل المنشور. لا تعتمد فترة السماح بوصفها بديلًا عن حماية
الجلسة من الاستيلاء؛ يحدد المسؤول مدتها بحسب سياسته.
