# دليل تطبيق الرسائل المختفية في الموبايل

تاريخ مراجعة المصدر: 9 نوفمبر 2026.

هذا دليل تنفيذ لمطوّر تطبيق الموبايل ليتكامل مع **الخلفية الحالية كما هي**
في مشروع `/home/marwan/سطح المكتب/workspace`.
إنشاء هذا الدليل لا يعني تعديل تطبيق الموبايل أو نشر الخلفية على الموقع.
لم يُحدد مستودع الموبايل، لذلك أسماء طبقات العمل أدناه وظيفية وليست مسارات
ملفات مؤكدة في تطبيقك.

## 1. السلوك المطلوب مطابقته

- الخيار داخل إعدادات المحادثة الفردية: إيقاف، 24 ساعة، 7 أيام، 90 يومًا.
- يبدأ الوقت من حفظ الرسالة على السيرفر، **وليس من قراءتها**.
- الرسالة تظهر عادية مباشرةً؛ لا تحتاج زر كشف أو إجراء «عرض مرة واحدة».
- يسري التغيير على الرسائل الجديدة ومرفقاتها. الرسائل السابقة تحتفظ بموعدها.
- تعديل النص أو تغيير المدة لا يعيد بدء مؤقت الرسائل السابقة.
- إيقاف الوضع لا يلغي مواعيد الرسائل المؤقتة التي سبق إرسالها.
- الردود داخل سلسلة مؤقتة لا تبقى بعد موعد رسالتها الأصلية، حتى لو أُوقف
  الوضع لاحقًا. رسائل النظام مستثناة.
- إعداد المحادثة مشترك بين الطرفين والأجهزة، وليس تفضيلًا محليًا للجهاز.

النطاق الحالي: محادثة فردية بين مستخدمين بشريين نشطين، وليست محادثة مع
النفس أو بوت أو محادثة مشتركة بين الخوادم. القنوات والمحادثات الجماعية
غير مدعومة. يلزم ترخيص مؤسسة مفعّل لتعديل الإعداد، وعضوية المحادثة مطلوبة
حتى لمدير النظام. لا يعتمد التنفيذ على تفعيل Burn-on-Read.

## 2. حقيقة التخزين في النسخة الحالية

| الموضع | ما يحدث الآن |
| --- | --- |
| `Posts` | تخزين الرسائل بالطريقة الأصلية، ثم حذف منطقي عند الموعد |
| `workspace_message_expiry.policies` | مدة المحادثة الحالية |
| `workspace_message_expiry.messages` | معرّف الرسالة وموعدها وحالة تنفيذ الحذف؛ ليس مخزن نص الرسالة |
| المرفقات | منع الوصول عند الموعد، مع حذف منطقي لمعلومات الملفات |
| قاعدة الموبايل | يطبّق العميل حالة الحذف ويزيل محتوى الرسالة من مخزونه المحلي |

هذه النسخة **لا تحفظ الرسائل في جدول محتوى مؤقت منفصل، ولا تمحوها نهائيًا
من قاعدة السيرفر أو التخزين أو النسخ الاحتياطية**. هذا يصف التنفيذ الحالي
المطلوب ربطه بالموبايل؛ لا تُعرض للمستخدم عبارة «لا تُخزّن الرسائل».

## 3. مواضع العمل داخل تطبيق الموبايل

استغل الطبقات الموجودة في التطبيق بدل إنشاء نظام مراسلة آخر:

| الطبقة الموجودة | الإضافة أو المراجعة |
| --- | --- |
| عميل REST لكل سيرفر | دالتا قراءة وحفظ إعداد الاختفاء |
| قائمة تفاصيل المحادثة | خيار «الرسائل المختفية» للمحادثات الفردية المؤهلة |
| شاشة أو Bottom Sheet للإعداد | الخيارات الأربعة، تحميل، حفظ، وأخطاء |
| قاعدة البيانات المحلية | تطبيق الحذف على النص والمرفقات والسجلات التابعة |
| معالج WebSocket | إعادة استخدام مسار `post_deleted` وتأكيد تنظيف البيانات المحلية |
| المزامنة والاستئناف | التقاط الحذف الذي حدث أثناء انقطاع الجهاز |
| تنزيل الملفات ومعرض الوسائط | إزالة الكاش الخاص بالتطبيق ومعالجة 404 |
| الترجمة والثيم | العربية والإنجليزية وRTL وألوان التطبيق القائمة |

لا يغيّر الموبايل جداول PostgreSQL ولا يستدعي قاعدة السيرفر مباشرةً.

## 4. عقد API الحالي

استخدم عميل الاتصال الموثّق الموجود لكل سيرفر، بما فيه تسجيل الدخول وMFA
ومعالجة انتهاء الجلسة. لا تنشئ عميلًا يتجاهل تحقق TLS أو يتجاوز مسار المصادقة.
لو كان العميل الأصلي يستخدم Bearer token، حافظ على آليته؛ لا تضع رموزًا
حقيقية داخل المصدر أو السجلات. المسارات أدناه كاملة من جذر الموقع؛ إذا كان
عميلك يضيف `/api/v4` تلقائيًا فلا تضف البادئة مرتين.

### قراءة الإعداد

```http
GET /api/v4/workspace/channels/{channel_id}/disappearing
```

الاستجابة الناجحة `200`:

```json
{"duration_seconds": 86400}
```

القيمة `0` تعني إيقاف الوضع للرسائل الجديدة؛ ليست دليلًا على أن كل الرسائل
الموجودة في المحادثة دائمة.

### حفظ الإعداد

```http
PUT /api/v4/workspace/channels/{channel_id}/disappearing
Content-Type: application/json

{"duration_seconds": 604800}
```

الاستجابة الناجحة `200` تحمل الإعداد الذي قرأه السيرفر بعد الحفظ:

```json
{"duration_seconds": 604800}
```

| النص | `duration_seconds` |
| --- | ---: |
| إيقاف | 0 |
| 24 ساعة | 86400 |
| 7 أيام | 604800 |
| 90 يومًا | 7776000 |

أرسل هذا المفتاح فقط. لا ترسل `enabled` أو `expires_at` أو `read_at`.
القيم الأخرى، الحقل المفقود، `null`، والحقول غير المعروفة مرفوضة.
قد يعيد الطرف الآخر تغيير الإعداد؛ اعرض قيمة استجابة السيرفر ثم أعد القراءة
عند فتح شاشة الإعداد مجددًا. لا تعتبر القيمة المحفوظة محليًا حقيقة دائمة.

### التعامل مع الأخطاء

| الحالة | تعامل الموبايل |
| --- | --- |
| `400` | رفض المدخلات؛ أبقِ الشاشة واعرض رسالة مناسبة |
| `401` أو متطلبات المصادقة الأصلية | طبّق مسار تجديد الجلسة أو MFA الموجود |
| `403` | راجع العضوية والترخيص وأهلية المحادثة؛ لا تفترض أن السبب ترخيص فقط |
| `404` لمسار الإعداد | قد تكون نسخة السيرفر غير داعمة أو الخدمة لم تُجهّز؛ لا تعرض نجاحًا |
| `503` أو خطأ اتصال | اسمح بإعادة المحاولة ولا تغيّر القيمة المعتمدة محليًا |

لا يوجد endpoint مستقل معلن لاكتشاف هذه القدرة. فتح شاشة الإعداد وإجراء GET
هو الفحص العملي الحالي. لا تفسّر خطأ الشبكة على أنه تعطيل الميزة إلى الأبد.

## 5. تجربة المستخدم

1. أضف «الرسائل المختفية» في تفاصيل المحادثة الفردية.
2. نفّذ GET عند فتح الشاشة؛ أظهر حالة تحميل وعطّل الحفظ حتى نجاحه.
3. اعرض الخيارات كاختيار واحد، وحدد القيمة الآتية من السيرفر.
4. عطّل الحفظ إذا لم تتغير القيمة أو كان الطلب قيد التنفيذ.
5. بعد نجاح PUT اعتمد قيمة استجابته وأغلق الشاشة؛ عند الخطأ أبقها مفتوحة.
6. إعادة فتح الشاشة تنفّذ GET جديدًا. لا تستخدم polling كل ثانية للإعداد.

نص الشرح المقترح:

> تبدأ المدة من وقت إرسال الرسالة، سواء قُرئت أم لا. يسري الإعداد على
> الرسائل الجديدة ومرفقاتها على جميع الأجهزة. تحتفظ الرسائل السابقة بموعدها.

السيرفر يرسل بالفعل رسالة نظام مشتركة عند تغيير الإعداد. لا يرسل الموبايل
رسالة ثانية ولا يحاول تحليل النص العربي لهذا الإشعار لاستخراج المدة.
استخدم مفاتيح ترجمة وثيم التطبيق ودعم RTL/LTR؛ أبقِ المعرّفات التقنية دون ترجمة.

## 6. إرسال الرسائل والمرفقات

استخدم الإرسال والرفع الأصليين:

- رفع الملف عبر مسار الملفات المعتاد والحصول على `file_ids`.
- إنشاء الرسالة عبر `POST /api/v4/posts` بالحقول الأصلية.
- الرسالة نوعها عادي؛ لا تحوّلها إلى `burn_on_read`.
- السيرفر هو الذي يسجل الموعد داخل معاملة حفظ الرسالة.

لا يرسل الموبايل موعدًا محسوبًا من ساعة الجهاز، ولا يستدعي حذف الرسالة
بنفسه عند انتهاء مؤقت محلي. هذا يمنع اختلاف النتائج بين الأجهزة أو عند
إغلاق التطبيق. احتفظ بمسار إعادة المحاولة ومنع تكرار الإرسال الموجود.

## 7. استقبال الحذف وتنظيف قاعدة الموبايل

السيرفر يستخدم الحدث الأصلي `post_deleted`؛ ليس هناك حدث خاص باسم
`disappearing_message_deleted`. الحقل `data.post` في الحدث نص JSON يجب فكّه
كما يفعل مسار الحذف الحالي في التطبيق.

عند استقبال الحدث:

1. حدد السيرفر والحساب والمحادثة والرسالة من سياق الاتصال والبيانات.
2. مرّر الحدث إلى معالج الحذف الأصلي لتحديث الرسالة والردود والعدادات.
3. أزل النص والمحتوى المشتق محليًا، وبيانات المرفقات ومعايناتها وفهارس البحث
   الخاصة بالتطبيق؛ لا تكتفِ بإخفاء صف العرض مع إبقاء النص في قاعدة الهاتف.
4. نظّف ملفات الكاش التابعة للرسالة، مع احترام أي مراجع محلية مشتركة لملف.
5. أغلق عارض المرفق إذا كان مفتوحًا، وأزل معاينة آخر رسالة والإشعارات المحلية
   المرتبطة بها حيث تدعم واجهات النظام ذلك.
6. إذا كان النظام يستخدم tombstone للمزامنة، احتفظ فقط بالبيانات اللازمة
   لمنع إعادة إدخال الرسالة، مع إزالة المحتوى. مؤشر «تم حذف الرسالة» مقبول
   ومتوافق مع واجهة الويب الحالية.

قد يتكرر الحدث أثناء التعافي؛ يجب أن يكون تطبيق الحذف idempotent دون إنقاص
العدادات مرتين. ولا يفترض العميل أن `delete_at` في كائن الحدث وحده هو الإشارة؛
نوع الحدث نفسه يحدد عملية الحذف.

هذه خطوات مطلوب تنفيذها أو التحقق منها في الموبايل، وليست ادعاءً بأن كاش
مشروع الموبايل الحالي نُظّف أو اختُبر بالفعل.

## 8. انقطاع الاتصال وإغلاق التطبيق

لا تعتمد على WebSocket وحده: قد ينتهي الموعد والهاتف مغلقًا أو غير متصل.
عند استعادة الاتصال أو الرجوع إلى التطبيق:

- استخدم مزامنة التغييرات الأصلية من السيرفر لكل محادثة محمّلة، مع نقطة
  مزامنة صحيحة والتعامل مع السجلات ذات `delete_at > 0`.
- إذا ضاعت نقطة المزامنة، نفّذ مصالحة موثوقة للنطاقات المحمّلة قبل اعتماد
  المحتوى القديم. غياب رسالة عن صفحة واحدة من النتائج لا يثبت أنها حُذفت؛
  احترم pagination ونطاق التغطية.
- لا تعِد إدخال نسخة قديمة من رسالة بعد معالجة حذف أحدث منها.
- لا تمسح كل الرسائل المؤقتة لمجرد وصول HTTP 404 واحد؛ نفّذ المصالحة في سياق
  المسار والصلاحيات وحالة الاتصال.
- احفظ آخر نقطة مزامنة بعد تطبيق التغييرات محليًا بنجاح، لا قبلها.

**قيد النسخة الحالية:** GET للإعداد لا يعيد مواعيد الرسائل، وكائن الرسالة
العادي لا يضيف `expires_at` خاصًا بهذه الميزة. لذلك لا يمكن استنتاج الموعد
الدقيق من `create_at + مدة المحادثة الحالية`؛ الإعداد قد تغيّر والردود قد
ترث موعد الأصل. ولا يوجد ضمان اختفاء دقيق على جهاز غير متصل قبل مزامنته.

إذا طُلب مستقبلًا اختفاء محلي دقيق دون اتصال أو عدّ تنازلي لكل رسالة، فهذا
يحتاج توسعة عقد السيرفر ليرسل الموعد المجمّد لكل رسالة ومرجع وقت مناسب.
هذه التوسعة غير موجودة ضمن الدليل أو التنفيذ الحالي.

## 9. المرفقات

عند الموعد يحجب السيرفر مسارات محتوى الملف والمعاينة والصورة المصغرة
والمعلومات. الروابط العامة للمرفقات المؤقتة غير متاحة حتى قبل انتهاء المدة.
استجابات هذه الملفات تحمل `Cache-Control: no-store`.

- احترم `no-store` في طبقة HTTP. راجع كاش مكتبة الصور/الفيديو أيضًا؛ قد
  تحفظ نسخة مستقلة رغم سياسة HTTP.
- إن احتاج العارض ملفًا مؤقتًا، اجعله داخل مساحة التطبيق واربط تنظيفه
  بإغلاق العارض والحذف وتسجيل الخروج، دون نسخه تلقائيًا إلى المعرض.
- عالج 404 بإغلاق العارض وإظهار «الملف غير متاح»، ولا تستمر بإعادة التنزيل
  في حلقة. قد يكون السبب حذفًا أو صلاحية، وليس دائمًا انتهاء المؤقت.
- لا تعد المستخدم بسحب ملف صدّره بنفسه إلى تطبيق آخر أو نزّله في مساحة عامة.

## 10. اختبارات القبول على Android وiOS

نفّذها على حسابات وقاعدة اختبار معزولة، وبنسخة سيرفر منشورة تتضمن الميزة:

| التجربة | النتيجة المطلوبة |
| --- | --- |
| فتح الإعداد دون تفعيله سابقًا | إيقاف، أو القيمة الفعلية إن غيّرها الطرف الآخر |
| حفظ كل مدة ثم إعادة فتح الشاشة | القيمة محفوظة من API وليست من ذاكرة الشاشة فقط |
| تغيير الإعداد من الويب ثم فتحه بالموبايل | يعرض الموبايل القيمة الجديدة |
| فشل GET أو PUT | رسالة خطأ دون نجاح وهمي أو إغلاق غير صحيح |
| إرسال نص ومرفق | يظهران مباشرةً دون زر كشف |
| انتهاء الموعد والعميل متصل | يصل الحذف وتُزال البيانات المحلية والكاش |
| تكرار حدث الحذف | لا يتكرر تغيير العدادات ولا يتعطل التطبيق |
| إغلاق الهاتف ثم انتهاء الموعد وإعادة فتحه | المزامنة تزيل النسخة القديمة |
| رسالة قبل التفعيل | تبقى |
| رسالة بعد الإيقاف | تبقى؛ الرسائل المؤقتة السابقة تحتفظ بموعدها |
| تغيير المدة أو تعديل النص | لا يمتد موعد رسالة سابقة |
| رد داخل سلسلة مؤقتة | لا يبقى بعد موعد الأصل |
| مرفق مفتوح لحظة الحذف | يغلق العرض ويُنظف كاش التطبيق |
| مستخدم غير عضو/سيرفر بلا دعم أو ترخيص | رفض واضح دون تغيير الإعداد |
| العربية والإنجليزية/الوضع الداكن | اتجاه وترجمة وتباين صحيح مع ثيم التطبيق |

لا تضف مدة 60 ثانية إلى تطبيق الإنتاج لتسريع الاختبار؛ السيرفر يرفضها.
في اختبار التكامل المعزول فقط يمكن تقديم موعد رسالة الاختبار في قاعدة
الاختبار، كما يفعل `native_integration_test.go`. لا تنفّذ SQL على بيانات
مستخدمين حقيقيين لهذا الغرض.
