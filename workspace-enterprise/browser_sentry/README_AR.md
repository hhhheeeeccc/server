# مراقبة أخطاء المتصفح عبر Sentry

تسجل حزمة Enterprise سياسة مستقلة في PostgreSQL وصفحة إدارة في
`/admin_console/environment/browser_sentry`. لا تتغير إعدادات Sentry الخاصة
بخادم Go (`LogSettings.EnableSentry`) ولا يُعدل `mattermost/server/`.
لإرسال أخطاء خادم Go إلى مشروعك راجع [إعداد Sentry للخادم](../server_sentry/README_AR.md).

الميزة معطلة افتراضيًا. يمكن للمسؤول ضبط DSN من نوع HTTPS وبيئة التشغيل
ونسبة عينات تتبع الأداء وإعادة عرض الجلسات وإرفاق تسلسل الاستدعاءات وإرسال
المعلومات الشخصية الافتراضية. الحفظ يحتاج صلاحية كتابة إعدادات Logging
ورخصة Enterprise؛ القراءة الإدارية تحتاج صلاحية القراءة. يحفظ التحديث رقم
إصدار، ويرد `409` عند تعارض تعديلين. يسجل التدقيق حالة الحفظ وخيارَي
التفعيل وReplay دون تسجيل DSN. لا تعيد الواجهة العامة DSN عندما تكون الميزة
معطلة أو الرخصة غائبة؛ وعند تعذر قراءة السياسة لا تبدأ مراقبة المتصفح.
قراءة السياسة وحفظها محدودتان بخمس ثوانٍ أو بمهلة الطلب الأقصر، فلا يبقى
طلب الإعداد أو الحفظ معلقًا عند نفاد اتصالات PostgreSQL. يرد حفظ جسم يتجاوز
4 KiB بحالة `413` سواء وقع التجاوز داخل JSON أو بعده، دون تغيير السياسة.
أثبتت اختبارات API والقاعدة الحالتين؛ نجح اختبار الحزمة و`go vet` في
1 أكتوبر 2026.

تستخدم متغيرات `WORKSPACE_BROWSER_SENTRY_ENABLED` و`_DSN` و`_ENVIRONMENT`
و`_TRACES_SAMPLE_RATE` بقيم بادئة `WORKSPACE_BROWSER_SENTRY` لإنشاء صف السياسة
فقط. بعد إنشائه تصبح القاعدة المشتركة مصدر الإعداد. القيم الأولية غير الصالحة
تترك الميزة معطلة وتسجل تحذيرًا. على المسؤول استعمال صفحة الإدارة بعدها.

بعد تحميل إعدادات التطبيق، تجلب الواجهة الإعداد العام وتبدأ SDK عند التفعيل
فقط. يستخدم Replay إخفاء جميع النصوص ومنع الوسائط، مع عينة 10% من الجلسات
و100% من الجلسات التي تتضمن خطأ. خيار إرسال المعلومات الشخصية معطل افتراضيًا
ويجب تمكينه صراحة. إذا عُطلت السياسة في الجلسة الإدارية، تغلق الواجهة
عميل Sentry الحالي. بقية المتصفحات تطبق التغيير عند إعادة التحميل.
عند تغيير السياسة داخل الجلسة نفسها ينتظر التطبيق إغلاق العميل السابق قبل
تهيئة الجديد، ويتجاهل استجابة إعداد أقدم تصل بعد الأحدث.
تزيل الواجهة معاملات الاستعلام وأجزاء `#` من `request.url` وأسماء معاملات
التتبع وعناوين URL في breadcrumbs قبل إرسالها إلى Sentry؛ هذا يحمي رموز
الروابط المؤقتة التي قد تظهر في هذه الحقول. اختُبرت أحداث الخطأ والأداء
وbreadcrumbs، ونجح اختبار Jest وفحص TypeScript وESLint. لا يشمل هذا
التنظيف نصوص الاستثناءات التي قد ينشئها كود آخر أو بيانات مضافة يدويًا إلى
الأحداث؛ يجب مراجعتها ضمن اختبار الخصوصية مع مشروع Sentry حقيقي.

## مقارنة نموذج الإدارة بالمشروع المرجعي

المشروع المرجعي `~/سطح المكتب/workspace` يعرض Sentry ضمن إعدادات الخادم
`SentrySettings` في صفحة `/admin_console/environment/sentry`. هنا تبقى
السياسة في واجهة Enterprise المستقلة `/admin_console/environment/browser_sentry`
لتجنب تعديل `mattermost/server/`. رُتبت الحقول كما في المرجع، وعُرض معدل
التتبع بقيم 0% و10% و20% و50% و100%. تتعطل الحقول التابعة عند إطفاء الميزة
مع الاحتفاظ بقيمها المحفوظة، ثم تعود قابلة للتحرير عند تفعيلها. اختلاف مسار
الإعداد ومصدر حفظه مقصود، ولا يتطلب تعديل إعدادات Go الخاصة بـSentry.

## التحقق والحدود

نجح `go test ./browser_sentry -count=1` لاختبارات الصلاحيات والحفظ والتعارض
والتحقق من DSN وغياب الرخصة وفشل قراءة صف السياسة بحالة `503`. نجحت اختبارات عميل HTTP وصفحة الإدارة وتهيئة
SDK، وفحص TypeScript وبناء الواجهة. يلزم اختبار متصفح فعلي مع مشروع Sentry
وموافقة سياسة الخصوصية، ورفع source maps لإظهار تسلسل الاستدعاءات المقروء،
وقياس كلفة Replay. لا يعني نجاح الاختبارات المحلية وصول حدث إلى خدمة Sentry.

في إعداد PostgreSQL الحي الذي يستخدم `binary_parameters=yes` يجب تمرير JSON
كنص إلى عمود `jsonb`. صُححت كتابة السياسة لذلك؛ بعد إعادة بناء الخادم
وإقلاعه عاد مسار الإعداد العام بحالة `200`، والميزة معطلة وDSN غير مكشوف.
نجح اختبار اتصال PostgreSQL مستقل بهذا الخيار في إنشاء السياسة وتحديثها،
ونجحت اختبارات مماثلة لسياسات Step-up MFA وفلترة IP.
