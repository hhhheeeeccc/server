# عقد فلترة IP السحابية

## نقطة الربط والقيد

`server/einterfaces/ip_filtering.go` يوفر `ApplyIPFilters` و`GetIPFilters`.
مسار `/api/v4/ip_filtering` في الكور يشترط `license.IsCloud()` ورخصة Enterprise.
سُجلت الحزمة من `enterprise/main.go` وتخزن السياسة في جدول
`WorkspaceIPFilters` مع رقم إصدار. هذه الحزمة لا تفتح المسار لرخصة استضافة
ذاتية. تتيح
`app.Srv().Router.Use` نقطة ربط لاعتراض طلبات HTTP التي تمر عبر موجّه
التطبيق، بما فيها API وWebSocket؛ وقد أضيف الإنفاذ داخل Enterprise دون
تعديل `server/`. هذا لا يثبت تغطية الطلبات التي لا تمر عبر ذلك الموجّه أو
مسارات CDN والموازن. يلزم اختبار النشر الفعلي عبر موازن الحمل قبل اعتبار
الحماية مكتملة.

`utils.GetIPAddress` يقبل أول قيمة من الترويسة المضبوطة في
`TrustedProxyIPHeader` دون أن يتحقق من عنوان الوكيل الذي أرسلها. لذلك لا
تستخدمه هذه الخدمة للإنفاذ. تعتمد `RemoteAddr` مباشرة ما لم تُضبط قائمتا
`WORKSPACE_IP_FILTER_TRUSTED_PROXIES` (CIDR مفصولة بفواصل) و
`WORKSPACE_IP_FILTER_CLIENT_HEADER` (اسم ترويسة واحدة مثل `X-Real-IP`) على
كل عقدة. عندئذ لا تُقبل قيمة الترويسة إلا إذا كان `RemoteAddr` ضمن قائمة
الوكلاء الموثوقين. يجب أن يستبدل الوكيل الترويسة ولا يمرر قيمة أرسلها
العميل؛ تُرفض القيمة المفقودة أو ذات عناوين متعددة من وكيل موثوق.
تُرفض أيضًا ترويسات العميل المكررة في أسطر HTTP منفصلة؛ يجب أن يقدم الوكيل
ترويسة واحدة بقيمة عنوان واحدة بعد استبدال ما أرسله العميل.
تُطبَّع نطاقات الوكلاء بصيغة IPv4 المضمّن في IPv6 إلى نطاقات IPv4 قبل
المقارنة، ويُرفض القناع الأوسع من مساحة IPv4 المضمّنة؛ اختُبرت الحالتان
مع عنوان وكيل IPv4 وقراءة عنوان عميل مختلف من الترويسة.
اضبط `ServiceSettings.TrustedProxyIPHeader` على الترويسة نفسها كي يعرض مسار
`/my_ip` الأصلي العنوان الذي تستخدمه الخدمة؛ هذا الإعداد لا يمنح الترويسة
الثقة لدى خدمة الإنفاذ من دون قائمة الوكلاء أعلاه.

تقرأ كل عقدة السياسة من قاعدة الكتابة المشتركة مع كل طلب؛ عند فشل القراءة
تُرفض الطلبات برد `503` ما دامت رخصة Cloud Enterprise فعالة. لا يضيف هذا
إنفاذًا إلى CDN أو موازن الحمل. يرفض مسار API قائمة تستبعد عنوان المسؤول
الذي يرسل طلب الحفظ. يفحص الوسيط جسم JSON كاملًا ويرفض بيانات لاحقة بعد
القائمة؛ لأن معالج API الأصلي يقرأ أول قيمة فقط، ما كان يمكن أن يتجاوز
فحص الاستبعاد الذاتي. اختُبر رد `400` وبقاء السياسة وإصدارها دون تغيير.
أما استدعاء واجهة Go مباشرة فلا يحمل عنوان الطلب،
ولذلك لا يملك فحص الاستبعاد الذاتي نفسه.
تتحقق القراءة أيضًا من شكل السياسة المحفوظة ومن صحة كل CIDR؛ سياسة `null`
أو CIDR تالف بسبب كتابة خارجية تعطي `503` بدل تحويلها إلى سماح للجميع.
القائمة الفارغة `[]` وحدها تمثل سياسة السماح غير المقيدة. اختُبر التلف
والاستعادة عبر قاعدة البيانات وطلب HTTP في اختبار التكامل المحلي.
قراءة السياسة في الوسيط محدودة بخمس ثوانٍ أو بمهلة الطلب الأقصر؛ إذا
نفدت المهلة أثناء انتظار اتصال قاعدة البيانات يعود `503` دون استدعاء
المعالج التالي. لا تجعل هذه المهلة تكلفة القراءة لكل طلب مقبولة تلقائيًا؛
يبقى قياس الحمل على نشر فعلي مطلوبًا.

## شروط التنفيذ

- تقبل CIDR صحيحة فقط، وتطبع IPv4/IPv6 وترفض التكرار. سياسة فارغة أو كل
  مدخلاتها معطلة تسمح بالمرور. يشترط الإنتاج إجراء استعادة إداريًا من قاعدة
  البيانات إذا حُظر المسؤول بسبب تغيير خارجي: يمكن لمسؤول قاعدة البيانات
  تنفيذ `UPDATE WorkspaceIPFilters SET Policy='[]'::jsonb, Version=Version+1 WHERE Id=1`
  لإزالة القيد، ثم مراجعة سجلات التدقيق وإعادة السياسة الصحيحة.
- نطاق IPv4 المضمّن بصيغة `::ffff:` يُحوّل إلى CIDR IPv4 قبل التخزين
  والإنفاذ؛ يُرفض قناع أوسع من مساحة IPv4 المضمّنة بدل حفظ سياسة لا تطابق
  عنوان العميل المطبع.
- يقرأ الإنفاذ السياسة مباشرة من قاعدة مشتركة بعد حفظها الذري؛ لا توجد بوابة
  مستقلة تُنشر إليها السياسة. تُراجع صلاحيات القراءة والكتابة وسجل التدقيق
  الموجودان في API الأصلي.
- واجهة Cloud المسجلة حاليًا تعيد خطأً صريحًا لخدمات CWS غير المتصلة؛ ذلك
  يمنع انهيار مسار البريد بعد حفظ السياسة، لكنه لا يحقق بيانات العميل أو
  إشعار مالك مساحة العمل أو اشتراك Cloud حقيقيًا.

## قبول الميزة

اختُبر API والصلاحيات وتطبيع CIDR ومنع استبعاد عنوان المسؤول، واعتراض طلب
مسموح ومرفوض ومنع تزوير ترويسة من عميل مباشر، واختيار عنوان IPv6 خلف وكيل
موثوق. نجح اختبار مثيلَي تطبيق مستقلين على قاعدة مشتركة: طبّقت العقدة
الأولى سياستين متتاليتين ورأت الثانية الرفض ثم السماح دون إعادة تشغيل.
اختبار محلي بمخزن سياسة مغلق أكد رد `503` حتى لعنوان كان مسموحًا، وعدم
استدعاء المعالج التالي، وفشل القراءة والكتابة الصريح، ثم نجاح القراءة من
اتصال قاعدة سليم. هذا يحاكي فشل الاتصال ولا يثبت زمن التعافي أو سلوك
انقطاع قاعدة إنتاجية متعددة العقد.
اختبار مستقل حجز الاتصال الوحيد في تجمع قاعدة منفصل وتحقق من رد `503`
بعد مهلة القراءة دون تمرير الطلب إلى المعالج التالي.
صارت واجهة الإدارة تحفظ مباشرة عند نجاح API، ولا تنتظر حالة تثبيت
CWS غير المتصلة؛ تعرض فشل الحفظ وتوضح مسار الاستعادة الإداري بدل رابط بوابة
عميل غير موصولة. تبقى تجربة جهازين فعليين وموازن وCDN وانقطاع قاعدة إنتاجية واختبار الحمل
واتصال Cloud الحقيقي قبل إعلان تكافؤ الميزة الرسمية.

## قياس محلي لمسار القراءة

أضيف `BenchmarkIPFilteringRequest` لقياس الوسيط المرخّص كاملًا، بما فيه
قراءة PostgreSQL المشتركة وفحص العنوان. أُعيد القياس بالأمر:

```sh
go test ./ip_filtering -run '^$' -bench '^BenchmarkIPFilteringRequest$' -benchtime=100x -count=1 -timeout=5m
```

على جهاز i9-12900H مع قاعدة اختبار محلية، كانت النتائج التقريبية للطلب:

| نطاقات السياسة | الزمن | التخصيصات |
| --- | ---: | ---: |
| 0 | 68 µs | 2.1 KiB |
| 1 | 115 µs | 2.3 KiB |
| 100 | 289 µs | 50.5 KiB |

هذا قياس تسلسلي محلي بمئة تكرار، ولا يثبت زمن الذروة أو throughput أو
كلفة قاعدة بعيدة أو سلوك عقدتين. إعادة القياس بحمل متزامن وبيانات إنتاج
وموازن حمل مطلوبة قبل اعتماد حد سعة لهذه الميزة. لا يُستخدم كاش قديم
لتسريع الطلبات لأن فقد قاعدة السياسة يجب أن يظل مرفوضًا.
