# قفل تغيير حالة الاتصال يدويًا

عندما تكون `TeamSettings.LockTeammateNameDisplay=true` وراية
`LockTeammateNameDisplay` موجودة في الرخصة، يعترض تنفيذ Enterprise طلب
`PUT /api/v4/users/{user_id}/status` قبل مسار الخادم الأصلي. يمنع المستخدم
العادي من اختيار متصل أو بعيد أو عدم الإزعاج أو غير متصل يدويًا، ويتيح
للمسؤول العام ومدير المستخدمين المخوّل إدارة مستخدمي فريقه التغيير.
يشمل القفل أوامر `/online` و`/offline` و`/away` و`/dnd` ومرادفاتها العربية؛
هذه الأوامر كانت تستدعي تغيير الحالة مباشرة وتتجاوز مسار `PUT`. لا يشمل
القفل الحالة النصية أو الإيموجي.

عند إطفاء الإعداد أو غياب الراية، يمر الطلب إلى مسار Mattermost الأصلي.
التحقق من الجلسة وMFA وهوية المستخدم وشكل الاستجابة محفوظ. تغيرات الحضور
التلقائية الناتجة عن الاتصال وانقطاعه ليست طلبات تغيير يدوي، لذلك تبقى
منفصلة عن هذا القفل. الحالة المخصصة النصية لها مسار API مستقل.

في المسار المقفل يُفحص تصريح المستخدم قبل قراءة جسم الطلب. جسم طلب المسؤول
محدود بـ8 KiB، ويُرفض JSON الزائد بعد كائن الحالة. عند الخطأ في قراءة
الحالة أو تعطيل الرد التلقائي يُستخدم نوع الخطأ الفعلي حتى لا يؤدي مؤشر
`AppError` الفارغ إلى انهيار معالج HTTP.
يُتحقق من قيمة الحالة قبل تعطيل الرد التلقائي. الطلب الذي يحمل حالة غير
معروفة يرد `400` ويبقي «خارج المكتب» والرد التلقائي كما كانا. أثبت ذلك
اختبار API `TestInvalidManualStatusDoesNotDisableAutoResponder`؛ نجح
`go test ./status_lock -count=1` و`go vet ./status_lock` في 1 أكتوبر 2026.

اختبار `go test ./status_lock` يغطي السماح قبل القفل، الرفض بعده عبر API
وأوامر اللغتين، بقاء القيمة القديمة، سماح المسؤول، رفض JSON زائد والجسم
الكبير، وحالتي إطفاء الإعداد وراية الرخصة. نجح الاختبار و`go vet
./status_lock` في 1 أكتوبر 2026. لا يمنع تغييرات الحضور التلقائية.
