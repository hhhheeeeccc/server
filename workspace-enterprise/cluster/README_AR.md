# التوافر العالي داخل workspace-enterprise

> أُرشفت أدوات جولة الفحص خارج مجلد المنتج. أوامر `audit/` أدناه
> توثق بيئة الاختبار السابقة؛ راجع [مكان الأرشيف](../docs/AUDIT_ARCHIVE_AR.md).


تُسجل الخدمة من `main.go` عبر `platform.RegisterClusterInterface(cluster.New)`،
وتنفذ واجهة `server/einterfaces/cluster.go` الحالية. تستعمل معالجات الخادم الأصلية
لأحداث WebSocket وإبطال الكاش وتحديث الحالة. لا تستبدل ملفات الخادم ولا تستعمل
Plugin Framework.

## التشغيل

- كل العقد تحتاج نفس هذا البناء ونفس قاعدة PostgreSQL ونفس مخزن الملفات المشترك.
  وجود مجلد `data` محلي مستقل على كل خادم لا يحقق مشاركة الملفات.
- يلزم ترخيص صالح يفعّل `Cluster`، و`ClusterSettings.Enable=true` واسم عنقود غير فارغ.
- تضبط عناوين `BindAddress` و`AdvertiseAddress` و`GossipPort` لكل عقدة. يجب أن تستطيع
  العقد الوصول إلى عنوان الإعلان ومنفذ gossip عبر TCP وUDP؛ القيمة الافتراضية 8074.
- تستعمل الخدمة `ClusterDiscovery` للاكتشاف و`Systems.ClusterEncryptionKey` للمفتاح
  المشترك عند تفعيل `EnableGossipEncryption`، وهو مفعّل افتراضيًا في إعدادات الكور.
  المفتاح يُنشأ مرة في قاعدة البيانات؛ لا يُكتب في التقرير أو سجلات الخدمة.
- تُنشأ `WorkspaceClusterLeases` تلقائيًا. تحتاج هوية قاعدة البيانات إذن إنشاء الجدول
  أول مرة؛ فشل التهيئة يُسجل ولا يُعلن نجاحًا وهميًا.
- تغييرات إعدادات النقل والترخيص التي تستدعي تشغيل مستمع جديد تحتاج إعادة تشغيل
  الخادم. لم تُضف آلية إعادة تشغيل حية لمستمع الشبكة.

## التنسيق والحدود

يُجدد القائد عقد قيادة مدته 8 ثوانٍ باستعمال وقت PostgreSQL كل ثانيتين. تتحقق
`IsLeader` من مهلة محلية أقصر بثانيتين، وتسقط القيادة عند فشل تجديد العقد.
مؤقت مستقل يبلغ مستمعي فقد القيادة عند انتهاء المهلة المحلية، حتى إذا لم يعد
استعلام PostgreSQL بسبب اتصال صامت. يعاد ضبط المؤقت عند التجديد، ويوقف عند
إلغاء العقد، ويمنع رقم جيل مؤقتًا متأخرًا من إلغاء عقد جُدّد بعده.

اتصال القرين البطيء يعمل في عامل منفصل حتى لا يؤخر التجديد. يطلب التوقف المنظم
إلغاء العمل الجاري وينتظر العمال ثم يحرر عقد القيادة وسجل الاكتشاف؛ فقد العملية
يعتمد على انتهاء العقد. تستخدم استعلامات تنسيق Cluster مجموعة PostgreSQL خاصة
بحد أقصى اتصالين، وبمهلة خمول ثانيتين لكل قراءة أو كتابة، تشمل اتصال إلغاء
الاستعلام الذي ينشئه `pq`. المهلة لا تمدد موعدًا أقصر يحدده برنامج التشغيل،
وليست مدة قصوى لاستعلام يواصل إرسال البيانات. يغلق التوقف مجموعة Cluster وحدها؛
لم تُغيّر اتصالات SQL أو برنامج التشغيل في الكور.

تُؤخذ إعدادات الرئيسية عند إنشاء الخدمة، كما يفعل `SqlStore` الأصلي عند إقلاع
الخادم. حفظ إعداد جديد أو إعادة تشغيل النقل وحده لا ينقل تنسيق القيادة إلى
قاعدة مختلفة عن قاعدة التطبيق الجارية؛ تغيير الرئيسية يحتاج إعادة تشغيل الخادم.
تُحفظ إعدادات DSN وTLS والتحقق من الشهادة دون إعادة تركيبها. إعدادات الاتصال
الخاصة بكل عقدة، ومنها مسارات الشهادات، تُدار بمتغيرات البيئة التي يدعمها الكور.

نقل أحداث التطبيق عبر TCP مشفر إذا كان تشفير gossip مفعّلًا. الرسالة ذات نوع
`reliable` تنتظر إقرار العقدة المستقبلة بعد استدعاء المعالج. رفض الحدث أو انتهاء
المهلة يظهر خطأ؛ واجهة البث العامة لا تعيد خطأ للمستدعي، لذلك تسجله الخدمة. النقل
ليس طابورًا دائمًا: لا تُحفظ الرسائل على القرص ولا يُضمن تنفيذها مرة واحدة عبر انهيار
عملية أثناء المعالجة. توجد حدود لحجم الرسالة (32 MiB) والطوابير وطلبات RPC المتزامنة.

تُنفذ طلبات الإحصاءات والسجلات وحزم الدعم وحالة الإضافات وعدد اتصالات المستخدم
وطوابير WebSocket ومزامنة الإعدادات عبر العقد. النتائج المجمعة هنا تخص العقد الأخرى؛
الكور يضيف نتيجته المحلية. تحفظ مزامنة الإعدادات إعدادات نقل العنقود الخاصة بالعقدة
المستقبلة. الإعدادات المحلية الأخرى ينبغي إدارتها بالطريقة التي يدعمها الكور، بما فيها
متغيرات البيئة. إعادة توزيع إعدادات ملف بوضع `ReadOnlyConfig` تخضع لرفض مخزن الكور.

## إبطال الكاش عند امتلاء طابور الإرسال

قد تنادي طلبات التطبيق وعمال الخلفية إبطال الكاش الأصلي بالتزامن مع
امتلاء طابور Cluster. تسجل الخدمة رقم الإبطال أولًا، ثم تحاول إدخاله
الطابور دون انتظار إذا كان نوعه `best_effort` وحدثه في قائمة الكاش
القابلة للاستعادة. يرسل المسار السليم إبطال المفتاح المعتاد، وتستعيد
مزامنة أرقام الكاش الإبطال الذي لم يجد خانة، أو يكشفه وصول رقم لاحق.
تستعمل الاستعادة معالج purge الأصلي للكاش المتأثر، دون حفظ مفاتيح أو
قيم أو إضافة طابور أو عامل لكل إبطال.

قد يضيف ذلك misses وقراءات SQL أثناء الضغط. التصحيح لاحق وخاضع للشبكة
ومدة push/pull وطابور الاستقبال والمعالجات، وليس مهلة اتساق صارمة أو
ACK لكل عقدة. يخص المسار أحداث الكاش المحددة وتسليم best_effort غير
المنتظر للجميع؛ يحافظ الإرسال الموثوق وأحداث التطبيق على عقدهما، وقد
ينتظران السعة. لا يوفر هذا سياق إلغاء لعمليات Redis أو فتح التخزين.

[إثبات الحجب والإصلاح والتحقق](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-outgoing-cache-pressure/README_AR.md).

## تصحيح الكاش عند تغير العضوية

قد تضيع إبطالات الكاش أثناء عزل gossip، وقد يموت مصدرها بعد تثبيت SQL وقبل
وصول الرسالة أو ملخص أرقامها. ينبه انضمام القرين وخروجه/موته عاملًا يجمع
أحداث الدفعة لمدة ثانية، ثم يرسل طلبًا داخليًا إلى مستقبل الرسائل التسلسلي.
تُستدعى محليًا معالجات localcachelayer الأصلية الـ34، ثم
`InvalidateAllCachesSkipSend` لتحديث الجلسات وWebConn والحالة والترخيص.
لا تُمحى رموز WebSocket الصالحة؛ تُرفض الجلسة الملغاة عند إعادة فحصها.

تبقى callbacks العضوية خفيفة، ويوقف العامل ويُنتظر مع بقية عمال النقل،
حتى عند امتلاء طابور المستقبل. لا يُبث `inv_all_caches` من هذا المسار؛
قد تبث API الأصلية إبطالات Channel/Post المحددة، فلا يعني SkipSend غياب
جميع الرسائل الشبكية. لا تعيد تلك الرسائل تنبيه مسار العضوية.

[إثبات الخلل عند إعادة الانضمام](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-gossip-partition/README_AR.md)
و[الإصلاح والتحقق بعد موت المصدر](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-source-crash-cache/README_AR.md).
لا يعيد هذا المسار أحداث WebSocket الضائعة.

### الكتابات اللاحقة لخروج القرين

يمكن لقرين معزول أن يواصل الكتابة في SQL بعد إشعار leave والمسح الأول، ثم
يموت بلا إشعار جديد. كذلك قد تبدأ عقدة دون معرفة الكاتب أصلًا. لذلك يطلب
عامل الاستعادة المسح كل 30 ثانية دون الاعتماد على اكتمال العضوية أو سجل
الاكتشاف، حتى لعقدة وحيدة ذات نقل عنقود مفعّل. يمر الطلب بالمستقبل التسلسلي
وبوابة الترخيص والتفعيل نفسها؛ لا تُنفذ المعالجات بلا ترخيص Cluster أو مع
`ClusterSettings.Enable=false`. هذه استعادة لاحقة وليست اتساقًا فوريًا أو
مهلة صارمة؛ يشمل التأخير انتظار الطابور وتنفيذ المعالجات الأصلية.

تُتبع نقاط gossip المفقودة، أي العنوان والمنفذ، لتجميع طلب المسح الفوري عند
أول رصد بدل تكراره مع كل محاولة اكتشاف. تزيل عودة العضو أو بديله المعرفة
بنقطته، دون تعطيل إعادة الفحص الدورية لكتّاب آخرين قد لا يُعرفون. تبقى
المعرفة عبر إعادة تشغيل النقل داخل الخدمة، لكنها لا تبقى بعد إعادة تشغيل
العملية. يحد التتبع بـ256 نقطة وعلم تجاوز محافظ؛ لا تعتمد الاستعادة الدورية
على هذا السجل أو على بقاء صف الاكتشاف بعد رصد الكاتب.

هذا يزيد cache misses وقراءات SQL وإعادة فحص الجلسات وإعادة تحميل الترخيص
حتى في العضوية السليمة، وليس ادعاء بتحسين الأداء. استُبدل شرط الدفعة السابقة
«قرين معروف مفقود فقط» لأن سجل الاكتشاف قد يكون ناقصًا أو غير مقروء.
[إثبات الخلل والإصلاح والتكلفة](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-discovery-independent-recovery/README_AR.md).

### بدء عقدة أثناء انقطاع gossip

يقارن عامل الاكتشاف نقاط SQL الحديثة بعضوية gossip قبل محاولات Join
المتسلسلة. إذا وجد نقطة غير متصلة، يطلب مسحًا فوريًا مجمعًا عند أول رصد
ويحتفظ بمعرفتها لمنع تكراره؛ لا يفرغ الكاش عند كل محاولة اكتشاف فاشلة.
لا يعتمد ذلك على صدور إشعار leave سابق، ولا ينشئ إشعارات عضوية وهمية. لا تمحو إزالة صف
الاكتشاف أو انتهاء صلاحيته معرفة الكاتب المفقود بعد رصده.

تُطابق نقطة IP واسم المضيف المسجل في metadata دون DNS داخل callbacks.
تزيل عودة العضو كلا الشكلين، وتستطيع عملية بديلة في النقطة نفسها إلغاء
المعرفة بغيابها. وجود العضو في نقطة لا يثبت اكتمال كل كتّاب SQL. يشترك الاكتشاف والمغادرات في سقف
256 نقطة؛ قراءة الصف 257 من نافذة SQL المحدودة تسجل علم تجاوز وتطلب المسح
الفوري مرة واحدة. قد تخفي الصفحة كاتبًا آخر؛ إعادة الفحص الدورية مستقلة
عنها وعن اكتمال هذه المطابقة.

تُنسخ بيانات الأعضاء في إشعارات Join وUpdate، وتُحذف عند Leave، ويقرأ
الاكتشاف وAPI حالة العنقود نسخة Enterprise المحمية بالقفل؛ لا يقرآن مراجع
metadata التي يعيدها memberlist خارج إشعاراته. تُصفّر لقطات الأعضاء الحيين
عند إعادة تشغيل النقل، مع إبقاء سجل الكتّاب المفقودين. حد 256 يخص النقاط
المفقودة؛ أما لقطات الأعضاء الحيين فبحجم العضوية الحالية.

نافذة الاكتشاف الحالية آخر 60 ثانية وللعنقود نفسه فقط؛ تفيد في بدء الاتصال
والمسح الفوري، ولا تتحكم بإعادة الفحص الدورية. اختُبر بدء عملية مع كاتب
بلا صف اكتشاف، ومع رفض PostgreSQL قراءة أعمدة الاكتشاف مع بقاء SQL التطبيق
والقيادة متاحتين. لا يُدّعى اختبار انحراف ساعات أجهزة فعلية؛ النبضة المحلية
لا تحتاج LastPingAt لاستدعاء الاستعادة. ولا يحول هذا الإبطال إلى سجل دائم
مع معاملة كتابة الكور، ولا يعالج تأخر نسخة SQL أو حجب معالجاتها الأصلية.
عولج لاحقًا مسار فشل البدء باستعادة محلية مستقلة؛ التفاصيل أدناه.
[الأدلة والحدود](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-discovery-independent-recovery/README_AR.md).

### فشل بدء النقل قبل إنشاء العمال

إذا أخفق بدء النقل، تُغلق مجموعة التنسيق ويبدأ عامل استعادة محلي بمؤقت
وطابور استقبال مستقلين عن حقول النقل التي تعيد المحاولات تهيئتها. يعيد
الفحص كل 30 ثانية عبر المستقبل الأصلي وبوابات الترخيص والتفعيل نفسها.
الإخفاق المتكرر لا يكرر العامل ولا يعيد مؤقته. يبقى خطأ النقل ظاهرًا،
ولا تعلن هذه الحالة عضوية أو قيادة أو توفر RPC وتوزيع أحداث WebSocket.

عند نجاح إنشاء المستمع وتسجيل العقدة، يتوقف العامل المحلي وينتهي أي
مسح جارٍ قبل نشر النقل وبدء المستقبل العادي. يوقف Shutdown العامل أيضًا
إن لم يوجد مستمع أصلًا. لا توجد إعادة محاولة تلقائية جديدة لبدء النقل؛
إذا استُدعيت دالة البدء لاحقًا استُخدم مسار الانتقال المختبر.

أُعيد إنتاج الخلل بعمليتين ورفض PostgreSQL الفعلي لقراءة `db_migrations`
أو تسجيل `ClusterDiscovery`، ثم تحقق تصحيح الاسم وHTTP401 وWS401 وبقاء
الاتصال الصحيح مع استمرار غياب النقل والقيادة. اختُبرت بوابات الترخيص
والتعطيل، والمحاولات الفاشلة المبكرة والمتأخرة، والانتقال والإيقاف.

المسح يرفع كلفة الكاش وSQL والجلسات وتحميل الترخيص. فترة المؤقت ليست
مهلة تعافٍ مضمونة. انتظار المعالجات الأصلية يحفظ تسلسلها، لكنه لا يحد
زمن SQL داخلها؛ حجبها قد يؤخر الإغلاق أو الانتقال إلى النقل.
[الأدلة والتكلفة والحدود](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-startup-failure-recovery/README_AR.md).

### حد مثبت: SQL الترخيص أثناء المسح والإغلاق

اختُبر المسح بترخيص محفوظ في `Licenses` و`Systems.ActiveLicenseId`، دون
`MM_LICENSE` داخل الطفل. نجح المسار السليم في مستقبل النقل وعامل فشل
البدء. عند صمت قراءة أي من الجدولين وصمت اتصال الإلغاء، بقيت العمليتان
منتظرتين بعد 10 ثوانٍ لكل فرع، رغم مهلتي استعلام واتصال ثانيتين في
الاختبار. أثبتت PostgreSQL دخول القراءة، وأثبتت المكدسات انتظار الإغلاق
لمستقبل داخل `LoadLicense`؛ استعادة SQL أنهت الانتظار للتنظيف.

هذا **غير محلول**: لا يوجد في المنافذ العامة المفحوصة مسح مكافئ كامل
بسياق قابل للإلغاء؛ لا يضمن `QueryTimeout` وحده إنهاء الاتصال الصامت.
لم تُعدل مجموعة SQL التطبيق أو معالجات الكور، ولم يُترك مستقبل موازٍ.
التحقق السابق للإغلاق مع SQL صامتة استخدم ترخيص البيئة، فلا يغطي هذا
المسار. [الإثبات والاختبارات والحدود](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-persisted-license-shutdown/README_AR.md).

## استعادة إبطال ضائع مع بقاء العضوية

ترافق أحداث إبطال الكاش المعروفة أرقام متزايدة لكل نوع ومرسل. تقارن مزامنة
memberlist الدورية الأرقام بالمعالج محليًا، وتستدعي معالج الكاش الأصلي لمسحه
إذا اكتشفت فرقًا. الأرقام المتتابعة السليمة لا تمسح الكاش، وفجوة وسط التسلسل
تسبب المسح قبل اعتماد الرقم الأعلى، فلا تُخفى الرسالة الضائعة بوصول التالية.
لا تحمل الحالة مفاتيح المستخدمين أو محتوى الكاش؛ حجمها محدود وعدّادات
القرائن محدودة. لا تُعاد أحداث التطبيق أو إضافاته عبر مسار استعادة الكاش.

الاستعادة لاحقة وليست اتساقًا فوريًا. تستعمل push/pull الأصلية بفاصلها
الافتراضي 30 ثانية وتوسعها بحسب حجم العنقود واختيار قرين عشوائي؛ لا يوجد
حد تعافٍ ثابت. العدادات محلية في الذاكرة، ويلزم توفر المصدر لمزامنتها؛
يعالج مسار تغير العضوية أعلاه موته قبل المزامنة في السيناريو المختبر.
يلزم البناء نفسه على العقد.
[إثبات الخلل والإصلاح والحدود](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/cluster-cache-anti-entropy/README_AR.md).

2. `TestSeparateProcessesTransportAndCrashFailover`: يشغّل نسختين من خادم الاختبار
   بعمليتين مستقلتين، لهما منافذ HTTP وTCP/UDP وذاكرات مؤقتة منفصلة، وقاعدة
   PostgreSQL ومجلد ملفات مشترك. يثبت إنشاء وقراءة الرسائل والملف عبر HTTP،
   ووصول أحداث WebSocket بالاتجاهين وإبطال كاش المستخدم بين العمليتين. يحجز صف
   عقد القيادة حتى تفشل عملية تجديده في كلتيهما، ثم يتحقق من استعادة قائد واحد.
   يقتل القائد فعليًا بـ`SIGKILL`، ويثبت استمرار HTTP وWebSocket لدى الباقي
   وانتقال القيادة إليه، ثم يعيد تشغيل العقدة ويثبت انضمامها ووصول رسالة منها.
   سحب ترخيص القائد يسقط قيادته وينقلها إلى القرين المرخص؛ سحب الترخيصين يمنع
   القيادة في كليهما. يتأكد الاختبار من انتهاء العمليات الباقية بنجاح عند التنظيف.
3. `TestSeparateProcessesDatabaseOutage`: يضع اتصال قاعدة كل عملية خلف وكيل
   TCP مستقل، ويحاكي قطع اتصالات قائد واتصالًا مفتوحًا يسقط جميع البيانات
   وطلبات إلغاء PostgreSQL. يتحقق من سقوط `IsLeader` ووصول إشعار المستمعين
   معًا، وانتقال عقد SQL إلى القرين، واستمرار HTTP وWebSocket لديه، ثم العودة
   إلى الخدمة بعد إصلاح الوصلة. يقطع وصلتي القاعدة ويثبت عدم وجود قائد، ثم
   يعيد وصلة واحدة ويثبت اكتساب القيادة مع بقاء المعزول دون قيادة. قاعدة
   PostgreSQL نفسها تظل متاحة للأب؛ هذا يحصر العطل في وصلة كل عقدة.
4. `TestSeparateProcessShutdownDuringSilentDatabase`: يطلب إيقاف خادم طفل
   فعلي بينما اتصال PostgreSQL مفتوح ويسقط البيانات في الاتجاهين. يتطلب خروجه
   بنجاح خلال 10 ثوانٍ دون إعادة الوصلة أو قتل الطفل لتحقيق شرط النجاح.
5. `TestSeparateProcessesGossipPartitionAndCacheRecovery`: عمليتان مستقلتان
   خلف وكيلَي TCP وUDP على loopback، مع تشفير gossip وبقاء PostgreSQL متاحة. يثبت
   خطأ reliable الظاهر وعدم تنفيذ الطلب المعزول، وانفصال العضوية مع استمرار
   قائد SQL واحد فوق مدة العقد وHTTP وWebSocket المحلي، ثم إعادة الانضمام
   والنقل بالاتجاهين وتصحيح كاش مستخدم ضاع إبطاله دون تعديل ثانٍ أو إعادة تشغيل.
6. `TestSeparateProcessesLostInvalidationWithoutMembershipChange`: إسقاط
   TCP أربع ثوانٍ مع مرور UDP وعضوية سليمة، وتغيير اسم وظهور كاش قديم ثم
   استعادته بالمزامنة الدورية دون تعديل ثانٍ أو إعادة تشغيل. تغطي اختبارات
   الأرقام فقد رسالة وسط التسلسل وتجاهل القديم والنسخ المكررة وعزل الأنواع.
7. اختبارات اتصالات التنسيق: صمت القراءة والكتابة، والمواعيد الأقصر وتصفيرها،
   وDSN غير صالح دون كشف أسرار، واتصال TLS فعلي مع `verify-full` ورفض شهادة
   لا تطابق الاسم أو غير موثوقة، وثبات الرئيسية حتى إعادة تشغيل الخادم وإغلاق
   المجموعة الخاصة دون إغلاق مخزن الكور.


8. `TestSeparateProcessesSourceCrashRecoversCachesAndRevokedSession`: تثبيت
   تغيير المستخدم وإلغاء جلسة في SQL مع إسقاط TCP وبقاء UDP، ثم SIGKILL
   فعلي للمصدر دون إعادة تشغيله أو فتح TCP. يشترط تصحيح الاسم وHTTP401
   وWS401 للجلسة الملغاة وبقاء اتصال WebSocket الصحيح وإرسال الرسائل.
   تغطي اختبارات العضوية أيضًا معالجات الكاش الـ34 واستثناء أحداث التطبيق
   ومسح الرموز القاطع، وتجميع التنبيهات وإيقاف العامل عند امتلاء الطابور.

9. `TestSeparateProcessesPostDepartureWritesRecoverAfterSourceCrash`: يثبت
   اكتمال مسح leave في سجلات العقدتين قبل تسخين الكاش وتغيير الاسم وإلغاء
   الجلسة. يقتل الكاتب مع بقاء TCP وUDP مقطوعين، ويشترط تصحيح الاسم وHTTP401
   وWS401 وبقاء اتصال WebSocket الصحيح، دون عودة الكاتب أو النقل.
   تغطي اختبارات إعادة الفحص العقدة الجديدة بلا معرفة بالكتّاب والعضوية
   السليمة والمغادرة وعودة عملية بديلة، وحد ذاكرة المعرفة بالقرائن المفقودة،
   وإعادة تشغيل العامل وإيقافه عند امتلاء طابور المستقبل.

10. `TestSeparateProcessesStartupDuringPartitionRecoversCachesAfterSourceCrash`:
    يبدأ وكيلَي TCP/UDP بالحجب قبل العمليتين، ويثبت عدم مرور بايتات TCP
    وعدم ظهور قرين بعيد، مع بقاء SQL. يسخن كاش العقدة الجديدة بعد اكتمال
    أي استعادة بدء موجودة، ثم يغير الاسم ويلغي جلسة ويقتل المصدر. يتطلب
    تصحيح الاسم وHTTP401 وWS401 وبقاء الاتصال الصحيح دون فتح النقل أو إعادة
    تشغيل الكاتب. تغطي اختبارات الاكتشاف تكرار المحاولات وأسماء المضيفين
    وIPv6 واستبدال العملية وحد الصفحة، وتزامنه مع callbacks العضوية.

11. `TestSeparateProcessesStartupWithoutDiscoveryRecoversCachesAfterSourceCrash`:
    يعيد حالة البدء المعزول مع غياب صف الكاتب أو رفض قراءة الاكتشاف. لا
    تتعلم العقدة الجديدة نقطة الكاتب، لكن الكاش والجلسة يصححان بعد قتله،
    مع HTTP401 وWS401 وبقاء الاتصال الصحيح وSQL متاحة والنقل محجوبًا.
    تستعمل حالة رفض القراءة مجموعة تنسيق اختبار بصلاحيات محدودة؛ لا تتغير
    مجموعة التطبيق ولا يوجد خيار منتج لاختيار قاعدة تنسيق مختلفة.

12. `TestPeriodicCacheRecoveryHonorsLicenseAndConfiguration`: يمرر نبضة
    إعادة فحص عبر العامل والمستقبل الحقيقيين؛ يثبت عدم استدعاء المعالجات
    بلا ترخيص أو بلا ميزة Cluster أو مع تعطيلها، ثم عودتها بعد التفعيل.

نقطة التحكم الإضافية موجودة في ملف `_test.go` فقط، بمسار loopback ورمز عشوائي؛

## ما لم يُثبت بعد

العمليات كلها على مضيف واحد. لم تُختبر أجهزة منفصلة أو موازن حمل أو انقسام
شبكة أجهزة فعلية أو ترقية PostgreSQL أو مخزن ملفات شبكي أو Redis أو حمل إنتاج.
اختبار الوكيل يثبت قطع اتصال TCP وصمته لكل عقدة، ولا يثبت سلوك موازن إنتاج أو
تحويل PostgreSQL إلى رئيسية بديلة أو تعطل أجهزة الشبكة الفعلية.
التحقق يقيس قرار القيادة والمالك في القاعدة؛ لا يشغّل مهام احتفاظ أو LDAP أو
ABAC طويلة، ولا يثبت منع تكرار آثارها بعد انهيار قائد أثناء التنفيذ.
مجموعة SQL الخاصة لا تفرض مهلتها على استعلامات الكور داخل بقية معالجات RPC
أو المهام؛ لا يثبت الاختبار حد إيقاف شاملًا في وجود أي عمل داخلي طويل.

عقد القيادة يعتمد على قاعدة رئيسية واحدة متسقة؛ تشغيل قاعدتين قابلتين للكتابة
بلا تنسيق خارج نطاقه. لا تضيف الخدمة fencing إلى كل مهمة داخلية طويلة في الكور.
زمن الانتقال في التجربة المحلية قياس لعينة واحدة، وليس التزامًا لبيئة النشر.

بروتوكول الرسائل هنا خاص بهذا التنفيذ. لا تخلط عقده بعقد Enterprise الرسمية بافتراض
توافق بروتوكول الشبكة. ملف `BasicCluster` في مشروع سطح المكتب يحوي دوال نقل فارغة؛
لذلك لم يُستخدم لإعلان التوافر العالي مكتملًا.
