# عامل الاحتفاظ بالبيانات

يعمل العامل المسجل من `enterprise/main.go` فقط عند وجود رخصة تسمح بالاحتفاظ
بالبيانات. تحذف الدفعات المنشورات والملفات التي تجاوزت حدود السياسات،
وتترك الملفات الحديثة وملفات الإشارات المرجعية. عند غياب الرخصة يفشل تنفيذ
المهمة قبل حذف أي منشور؛ يغطي اختبار تكامل هذه الحالة. يعيد العامل فحص
الرخصة قبل كل دفعة حذف وقبل كل ملف؛ عند إزالتها أثناء التشغيل يتوقف قبل
الدفعة أو الملف التالي. اختُبر توقف دفعات الرسائل، وحذف أول ملف ثم بقاء
الملف التالي عند سحب الرخصة. إذا بدأ حذف جسم ملف قبل السحب، يُكمل حذف سجله
لتجنب بقاء سجل يشير إلى جسم مفقود.

إذا توقف العامل لإغلاق الخادم، يعيد المهمة من `in_progress` إلى `pending`
لتستأنف بعد التشغيل. الإلغاء الصريح ينتقل من `cancel_requested` إلى
`canceled`؛ النجاح والخطأ لا يكتبان فوق طلب إلغاء وصل متأخرًا. تستخدم
الانتقالات شرط الحالة السابقة ومعرّف المحاولة الجديدة، وتنشر إشعار المهمة
عند نجاحها؛ يُسوّى مقياس النشاط المحلي عند خروج التنفيذ.
يمسك العامل قفل جلسة PostgreSQL على اتصال خاص واحد، وتنفذ عليه عمليات
الحذف وسجل معرّفات الرسائل المحذوفة وتنظيف الصفوف اليتيمة وبيانات الملفات.
إذا مات الاتصال، يتوقف DELETE الجاري معه؛ يرفض موصل المهمة إعادة الاتصال
التلقائية من `database/sql`. تحصل المهمة التالية على اتصال وقفل جديدين.
لا يحجز العامل اتصال القفل من مجموعة التطبيق، ويعمل مع حد اتصال واحد فيها؛
لكل تنفيذ منتظر أو جارٍ اتصال إضافي خاص يجب احتسابه ضمن ميزانية PostgreSQL.
تستخدم كتابة حالة المحاولة اتصالًا خاصًا مؤقتًا آخر لتسوية الحالة بعد فقد
اتصال التنفيذ؛ يجب احتساب هذا الاتصال أيضًا عند إنهاء مهمة. تُقرأ الملفات
من مخزن التطبيق؛ أما مطالبة المهمة وتسوية حالتها فتحميهما جلسة SQL ومعرّف المحاولة.

المخزن المحدود في `execution_store.go` يحافظ على خوارزمية SQL المرجعية:
أولوية سياسة القناة على الفريق، وأولوية السياسات الخاصة على العامة،
وحماية المنشور المثبت، وحفظ معرّفات الحذف في معاملة الحذف نفسها.
يقارن `execution_store_integration_test.go` النتائج والمؤشرات مع مخازن
الكور الأصلية على مخططين مستقلين. تحتاج هذه النسخة متابعة عند تحديث SQL
المرجعي؛ لا تستدعي مُنشئ `SqlStore` أو مجريشن أو تنظيف تفضيلات بدء التشغيل.
اختُبر العامل الحقيقي بقتل اتصال القفل أثناء DELETE محجوب: فشل العامل
الأول قبل تحرير حجب الجدول، ثم بدأ الثاني وحده وأبقى الرسالة الحديثة.
[الأدلة والنتائج والحدود](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/retention-lock-loss/README_AR.md).

يتطلب قفل الجلسة اتصالًا مباشرًا بـPostgreSQL أو وسيطًا يحافظ على الجلسة؛
لا يفترض دعم PgBouncer بوضع تجميع المعاملات. فحص الجلسة قبل إزالة جسم
الملف يمنع بدء الإزالة بعد اكتشاف فقدها، لكنه لا يلغي طلب مخزن خارجي بدأ
قبل الفقد. عولج محليًا بقاء الوصف بعد نجاح الجسم وفشل SQL: تُغلق جلسة
التنفيذ الأصلية، وتحاول جلسة مستقلة بقفل الاحتفاظ نفسه إكمال وصف الملف
الذي بدأ فقط. تطابق المعرّف ومسارات الجسم والمعاينات والمالك وأزمنة النسخة؛
الوصف الغائب يُقبل كإكمال سابق والمتغير يُحافظ عليه. لا تبدأ الجلسة الجديدة
حذف جسم أو دفعة، وتبقى المهمة الأصلية بخطأ أو بحالة الإلغاء/الإيقاف.
ميزانية السياق 30 ثانية أو مهلة SQL إن كانت أقصر، ثم يُسجل الفشل ويُترك
الوصف لتنفيذ لاحق عند تعذر الاتصال أو القفل. تستمر تسوية هذا الملف بعد
سحب الترخيص أو الإلغاء أو الإيقاف لأنه بدأ قبلها، وفق السلوك السابق.
[الأدلة وحدود الإكمال](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/retention-object-delete-loss/README_AR.md).
أُضيف مسار مستقل لفقد رد الحذف: تُفحص نتيجة كل مسار من الجسم والمعاينة
والمصغّر. عند خطأ الحذف يؤكد العامل الغياب من المخزن؛ إذا تعذر التأكيد
أو بقي الجسم، يُحافظ على `FileInfo` ويوقف التنفيذ. إذا ثبت غياب المسارات
كلها، يُكمل الوصف ثم يعيد خطأ التخزين ويتوقف قبل الملف التالي. لا تُتجاهل
أخطاء المعاينات كما في مساعد الحذف العام؛ يبقى الوصف حتى يستطيع تنفيذ
لاحق الوصول إلى مساراتها. لا يعالج هذا أجسامًا يتيمة حُذف وصفها بالسلوك القديم.

اختُبر أيضًا قتل عملية فعلية بعد نجاح DELETE وقبل رد المخزن، ثم تنفيذ
جديد في عملية مستقلة على الجهاز نفسه وبالقاعدة نفسها، على MinIO وAzurite.
بقي وصف الملف ومسارا معاينتيه بعد القتل؛ أكمل التنفيذ الجديد حذفها مع
الملف المنتهي التالي، وأبقى الحديث وملف الإشارة المرجعية. هذا يعتمد على
`FileInfo` المحفوظ، ولا يضيف intent دائمًا آخر لمسارات الملف. يبدأ التنفيذ
اللاحق برخصة اختبار صريحة وسياسة مفعّلة. الاختبار الأول يستدعي `execute`
مباشرة؛ أُضيف اختبار مهمة فعلية مستقل في الجولة الأحدث أدناه.
[الأدلة وحدود فقد الرد وموت العملية](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/retention-ambiguous-delete/README_AR.md).
لا توجد معاملة ذرية بين SQL والمخزن أو قدرة على منع DELETE سبق إرساله.
لا تثبت هذه الجولة سقوط عمليتين على جهازين أو تبديل قاعدة الكتابة.
عولج صمت اتصالات PostgreSQL الخاصة في متابعة مهلة SQL أدناه؛ تبقى
اتصالات الكور والتخزين الخارجي خارج هذه الحماية.
اختُبر الإيقاف والإلغاء وسباقهما مع النجاح والخطأ. حذف البيانات الذي اكتمل
قبل الإيقاف أو الإلغاء نهائي ولا يُسترجع؛ تستأنف الدفعات الباقية عند إعادة
تشغيل المهمة. يفحص العامل الإيقاف قبل تنظيف الصفوف اليتيمة وبين عناصر
دفعات التفاعلات وقبل إزالة جسم الملف. إذا بدأت إزالة جسم الملف، يحاول إكمال حذف
سجله على اتصال التنفيذ نفسه، ثم محاولة إكمال SQL المستقلة المحدودة عند فشله. واختُبر إلغاء مهمة قبل أول دفعة
مع بقاء المنشور المنتهي دون حذف.

اختُبر حذف الملف المنتهي وسجله مع إبقاء الملف الحديث وملف الإشارة المرجعية
على ثلاثة مخازن: المحلي، وMinIO عبر إعداد S3، وAzurite عبر إعداد Azure Blob.
اختُبرت أيضًا سياسة قناة وسياسة فريق مكتوبتان مباشرة في جداول الكور قبل
تشغيل واجهة Enterprise: ظهرتا عبر API، وحذف العامل رسالة منتهية في كل
نطاق، وأبقى رسالة حديثة. هذا يثبت توافق البيانات مع صيغة الجداول الحالية،
ولا يمثل تجربة بيانات إنتاج. نُفّذ ملف ترحيلة PostgreSQL
`000053_create_retention_policies.up.sql` الحقيقي مرتين على قاعدة اختبار
مستقلة تحوي شكلًا تمثيليًا للجداول والفهرس قبل هذه الترحيلة. بقيت السياسة
وروابط الفريق والقناة وقيمة المدة، وتغيّر الفهرس، وعملت قيود الحذف
المتسلسل. تتطلب إعادة الاختبار صلاحية إنشاء قاعدة؛ ينظف الاختبار قاعدته
بعده. لا يثبت ذلك تسلسل جميع ترحيلات إصدار قديم أو سلامة قاعدة الإنتاج.
تتطلب اختبارات المحاكيين المتغيرين `WORKSPACE_TEST_MINIO_ENDPOINT` و
`WORKSPACE_TEST_AZURITE_ENDPOINT`. عند استخدام Azurite 3.34.0 مع Azure SDK
الحالي، شغّله بخيار `--skipApiVersionCheck`؛ دونه يرفض المحاكي إصدار API
`2026-06-06` قبل بدء الاختبار. نجح اختبار العامل بهذه المتغيرات، ونجح
`go vet ./data_retention ./data_retention_job`.

المحاكيات لا تثبت سلوك حسابَي Amazon S3 وAzure Blob الإنتاجيين أو صلاحياتهما
أو انقطاع الشبكة. يلزم اختبار الحسابين الحقيقيين وبيانات إنتاج ممثلة قبل
اعتبار تشغيل الحذف في تلك البيئة متحققًا.

تحقق دفعة فقد رد المخزن السابقة: الحزمة كاملة **30 اختبارًا رئيسيًا و91 حدث نجاح**
بما فيها المخازن الثلاثة وفقد الجلسة وفقد رد الحذف وSIGKILL الفعلي ثم
إكمال مسارات الملف بعملية جديدة، وحالات المهمة الفعلية عند سحب الترخيص
والإلغاء والإيقاف. ونجح فحص `-race` المحدد **13 اختبارًا رئيسيًا و63 حدث نجاح**؛
دون فشل أو تخطٍّ في الجولتين. نجح vet للحزمتين. حُفظ المصدر والبصمات
وأُزيلت حاويات الاختبار؛ بقي الكور و`main.go` والتبعيات وحاوية
`workspace-minio` دون تغيير. لا يغلق ذلك حدود الانقطاع والعقد والتخزين
الخارجي وإعادة جدولة المهمة بعد القتل المذكورة أعلاه.

## استعادة مهمة عالقة بعد موت العملية

يفحص العامل المهام عند بدء `Run` ثم كل 30 ثانية، بشرط رخصة احتفاظ وسياسة
مفعّلة. يجرب قفل الاحتفاظ دون انتظار؛ إذا كان مشغولًا يترك المهام الجارية.
عند امتلاك القفل يعيد ما يصل إلى 100 محاولة معروفة من `in_progress` إلى
`pending`، وينهي `cancel_requested` إلى `canceled` بدل إحيائها. المراقب
الأصلي يعيد إرسال المهام المنتظرة؛ فترته الافتراضية 15 ثانية، وقد تؤخر
مهمة جارية الفحص التالي. لا يعتمد القرار على عمر `LastActivityAt`.

يحصل `doJob` على قفل جلسة الحذف قبل المطالبة بالمهمة، وتكتب الجلسة نفسها
معرّفًا جديدًا في `Data.workspace_retention_attempt_v1` مع تغيير الحالة إلى
`in_progress` ذريًا. الجلسة المفقودة لا تستطيع المطالبة من اتصال بديل.
تطابق كل كتابة تقدم أو حالة أو خطأ أو panic معرّف المحاولة؛ لا يستطيع
عامل قديم إنهاء مطالبة أحدث، ولو عادت إلى `in_progress`. تنقص مقاييس
المهام النشطة مرة واحدة عند خروج تنفيذ العملية الحالية، وتُنشر تغييرات
الحالة عبر حدث المهمة الحالي وصلاحياته.

تُستعاد فقط المطالبات التي تحمل معرّف هذا البروتوكول. مطالبة إصدار أقدم
لا تثبت امتلاك القفل قبل المطالبة؛ تُترك حالتها للمراجعة ولا يُخمن موتها.
يجب أن تطبق جميع عقد العمال البروتوكول نفسه؛ لا يثبت الاختبار تشغيل عمال
من الإصدار القديم والجديد معًا أو ترقية الإنتاج أثناء تنفيذ حذف.

اختبار العملية الجديد يحفظ Job حقيقية، ويسجل واجهة العامل في ثنائي
الاختبار، ويستعمل `JobServer.StartWorkers` والمراقب الأصلي. بعد SIGKILL
وصلت المهمة ذات المعرّف نفسه إلى النجاح عبر عملية جديدة دون تغيير حالتها
يدويًا. اختُبر ذلك على MinIO وAzurite، مع استكمال المسارات وحماية الملفات.
واختُبر قتل جلسة SQL فعلية، ومنع تحديث التقدم والنجاح والخطأ وpanic
والإيقاف والإلغاء من محاولة قديمة، وحماية محاولة نشطة ذات تاريخ قديم،
واحترام الترخيص والسياسة والإلغاء ونوع المهمة.
[أدلة استعادة المهام وحدودها](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/retention-job-crash-recovery/README_AR.md).
ميزانية السياق لكل تسوية حالة 30 ثانية ومهلة SQL إن كانت أقصر. أضيف
قطع مآخذ الجلسات الخاصة عند انتهاء السياق في المتابعة أدناه؛ لا يثبت
ذلك حدًا كليًا للإغلاق يشمل SQL الكور والتخزين الخارجي.

تحقق سابق قبل قطع صمت SQL: الحزمة كاملة **33 اختبارًا رئيسيًا و96 حدث نجاح**،
وفحص `-race` المحدد **16 اختبارًا رئيسيًا و68 حدث نجاح**، وvet للحزمتين؛
دون فشل أو تخطٍّ في الجولتين. تتضمنان اختبار الاستئناف المباشر للملفات
واختبار إعادة إرسال Job نفسها عبر عمال الخادم، على المخزنين. حُفظ المصدر
والبصمات، ونُظفت حاويات الجولات، وبقي الكور والتسجيل والتبعيات وMinIO
القائم دون تغيير. تبقى حدود البروتوكول القديم والعقد والخدمات الخارجية
واتصالات SQL الأصلية في الكور المذكورة أعلاه.

## قطع صمت SQL في جلسات الاحتفاظ الخاصة

تتتبع كل جلسة خاصة مآخذ المصافحة والاستعلام واتصال إلغاء pq المنفصل.
عند انتهاء سياق SQL تغلقها وتلغي الاتصال الجاري، وتبقى غير قابلة
لإعادة الاتصال. يلزم تنفيذ جديد يملك قفلًا جديدًا لاستئناف العمل.
لا تُغلق مآخذ مجموعة التطبيق أو تُعدل إعداداتها. عند نجاح SQL ينظف
مراقب السياق قبل إلغائه، فتُعاد الاستفادة من backend وقفل الجلسة.

يحد QueryTimeout الموجب كل عملية؛ الافتراضي 30 ثانية إن لم يكن موجبًا.
مهلة إنشاء TCP الأصغر منه ومن خمس ثوانٍ، وتضبط الجلسة وحدها
`statement_timeout` و`client_connection_check_interval=100`. يبقى
`application_name` وSSL من DSN كما حددهما المستدعي. الصيغتان URL
والكلمات المفتاحية مشمولتان بالتحقق. هذا يتطلب PostgreSQL 14+؛ الفحص
على 16. لا يتغير منطق اختيار السياسات أو معاملة الحذف وسجل معرّفاته.

يمر انتظار القفل بسياق قابل للقطع عند Stop أو إلغاء المهمة. تشمل
الحماية مطالبة المهمة والاستعادة والتقدم والإنهاء وإكمال وصف ملف حذف
جسمه؛ تبقى ميزانية الإكمال المستقل وحماية نسخته كما كانتا. لا يعني
فقد الرد أن DELETE لم يلتزم، ولا تُعاد البيانات التي حُذفت بالفعل.

أثبت التحقق الموجه فشل الأصل أمام مصافحة صامتة، ثم رجوع SQL وقطع
طلب إلغاء صامت وتحرير قفل DELETE حقيقي قبل رفع حجب Posts؛ لم ينفذ
العامل القديم حذفًا متأخرًا، وأكمل مالك قفل جديد الحذف.
نجح التحقق التراكمي النهائي بـ**41 اختبارًا رئيسيًا و112 حدث نجاح**
مع `-race` و`go vet` وPostgreSQL 16 وMinIO وAzurite، دون فشل أو تخطٍّ.
ثبت المصدر المختبر والكور والتسجيل والتبعيات ونُظفت الحاويات المؤقتة.
تبقى قراءات
الرخصة والسياسة ومراقب إلغاء الكور خارج جلسات الحماية، فلا تدعي هذه
الدفعة مهلة كلية لكل Stop أو حل طلب تخزين جارٍ أو تبديل الرئيسية.
لا يثبت إغلاق المأخذ حدًا صارمًا لتحرير قفل الخادم عند ابتلاع الشبكة
إشعار الإغلاق؛ مهلة العبارة وحدها لا تنهي قفلًا تابعًا للجلسة.
الكلفة مراقب لكل عملية وتتبع المآخذ وفحص اتصال العميل عند استمرار SQL؛
لم يُقَس حمل الإنتاج. لا خدمة خارجية جديدة ولا نشر في هذه الجولة.
[الأدلة والجولات والحدود](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-18/retention-sql-deadlines/README_AR.md).
