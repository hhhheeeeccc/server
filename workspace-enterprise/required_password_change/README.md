# إلزام تغيير كلمة المرور

تسجَّل مسارات الميزة من Enterprise، وتحتاج جلسة وصلاحيات إدارة المستخدمين وترخيصًا فعالًا.

## إعداد لوحة التحكم والحسابات الجديدة

في **إعدادات الموقع ← المستخدمون والفرق** (`/admin_console/site_config/users_and_teams`)، يظهر خيار **إلزام المستخدم بتغيير كلمة المرور بعد إعادة تعيينها بواسطة المسؤول**، وهو مفعّل افتراضيًا. عند تفعيله، يقبل إعادة التعيين الإداري كلمة مؤقتة مثل `1234` دون شروط الحد الأدنى والتعقيد. عند تعطيله، تخضع إعادة التعيين الدائمة لشروط الخادم المعتادة. لا يستطيع طلب إعادة التعيين تعطيل الإلزام الذي تفرضه السياسة.

إنشاء الحساب من نافذة الإدارة أو ملف Excel يستخدم المسار الإداري الجديد، ويقبل كلمة مؤقتة قصيرة وبسيطة، ويفرض تغييرها عند أول دخول **حتى إذا كان إعداد إعادة التعيين معطّلًا**. تبقى شروط كلمة المرور الدائمة والتسجيل العام وتغيير المستخدم لكلمته كما هي. لا تُقبل كلمة فارغة أو كلمة تتجاوز الحد التقني الأصلي (72 بايت).

المسارات:

- `GET /api/v4/workspace/required_password_change/policy`: قراءة الإعداد؛ تحتاج صلاحية قراءة صفحة المستخدمين والفرق أو إدارة المستخدمين.
- `PUT /api/v4/workspace/required_password_change/policy`: تعديل `require_on_admin_reset` مع `version`؛ تحتاج صلاحية كتابة صفحة المستخدمين والفرق. يُرفض تعارض الإصدار برمز 409.
- `POST /api/v4/workspace/users`: إنشاء حساب محلي مؤقت؛ يحتاج صلاحية إدارة المستخدمين. يقبل حقول الحساب الأساسية فقط، ويرفض حقول الأدوار ومصدر المصادقة.

تُحفظ السياسة في `WorkspacePasswordPolicy`، ويظل قرار الإلزام لكل حساب في `WorkspaceRequiredPasswordChange`. تُستخدم عملية الإنشاء الأصلية للمحافظة على التحقق من الحساب وحدود الترخيص والأدوار، مع كلمة تمهيدية عشوائية لا تُشارك مع أحد. تُثبّت حالة الإلزام قبل تثبيت كلمة المسؤول المؤقتة. تعالج `user_no_email.CreateLocalUser` البريد الفارغ عبر مسار التوافق الموجود، ثم تعيده فارغًا قبل الرد. لا ترسل عملية الإنشاء هذه بريد ترحيب؛ توزيع بيانات الدخول المؤقتة يتم خارجها. إذا فشل التخزين بعد إنشاء السجل وقبل تثبيت كلمة المسؤول، قد يبقى حساب بكلمة تمهيدية مجهولة؛ يمكن للمسؤول إصلاحه بإعادة التعيين بعد معالجة سبب الخطأ.

## الحسابات دون بريد

كان حفظ علامة `require_password_change` عبر `PatchUser` يفحص بيانات الحساب كاملة، فيرفض البريد الفارغ قبل إعادة تعيين كلمة المرور.

للحسابات دون بريد، يُحدّث المسار علامة الإلزام ووقت التحديث مباشرةً في قاعدة البيانات باتصال الخادم الحالي. دمج JSON يتم داخل عبارة SQL واحدة للحفاظ على الخصائص الأخرى. يبقى البريد فارغًا دون استخدام عنوان بديل. يُبطل كاش المستخدم ويُنشر تحديث منقّح إلى جلساته. يُتجاوز إشعار البريد عند إعادة التعيين الإداري للحساب دون بريد.

يُستخدم دمج JSON الذري نفسه للحسابات ذات البريد أيضًا، حتى لا يمسح حفظ علامة الواجهة خصائص أخرى عُدّلت بالتزامن. لا يتغير فحص الصلاحيات أو الترخيص أو كلمة المرور الحالية عند إكمال التغيير.

تحتاج حماية الإلزام إلى جدول خاص بالخادم `WorkspaceRequiredPasswordChange`؛ يُنشأ وتُرحّل العلامات السابقة عند تسجيل الخدمة داخل معاملة. لا تحتاج خدمة خارجية جديدة. يلزم إعادة بناء الخادم وتشغيل البناء الجديد لتطبيقه؛ تعديل المصدر وحده لا يحدّث العملية الجارية.

## الاختبار

من مجلد `workspace-enterprise`:

```bash
go test ./required_password_change -count=1
python3 required_password_change/run_integration.py
```

يستخدم اختبار التكامل PostgreSQL 16 مؤقتًا عبر Unix socket دون فتح منفذ TCP، ويحذفه عند الانتهاء. لا يستخدم إعدادات قاعدة النشر. يمكن تحديد مكان أدوات PostgreSQL بمتغير `PG_BINDIR`.

التغطية: إعادة التعيين والإلزام والإكمال والدخول بكلمة المرور الجديدة لحساب ببريد وآخر دون بريد، إلغاء إلزام سابق، الحفاظ على البريد والخصائص الأخرى، ورفض إعادة التعيين الإداري من مستخدم عادي برمز 403.

تشمل أيضًا قبول `1234` مع سياسة خادم تتطلب 12 حرفًا وجميع شروط التعقيد، رفض كلمة دائمة ضعيفة، حفظ السياسة وتعارض إصدارها، وفرض أول دخول للحسابات الجديدة ذات البريد وبدونه رغم تعطيل إعداد إعادة التعيين.

## حماية الإلزام على الخادم

`Props.require_password_change` إشارة للعرض فقط. القرار المعتمد محفوظ في الجدول الخاص، ولا تستطيع طلبات تحديث الملف الشخصي تغييره. تمنع بوابة Enterprise استخدام API العادي وWebSocket وواجهات الإضافات قبل إكمال التغيير، مع استثناءات محددة لعرض شاشة الإلزام وإكمالها وMFA والخروج. يُبطل التعيين الإلزامي الجلسات السابقة؛ الإكمال يطابق إصدار الإلزام ليحمي إعادة تعيين إدارية أحدث. تُحفظ صفوف الإلزام المكتملة حتى لا تعيد علامة قديمة ترحيلها إلى حالة نشطة.

الفحص يقرأ الحالة بالمفتاح الأساسي لكل طلب محمي مصادق عليه؛ لا يُستخدم كاش قديم يسمح بتأخير تطبيق قرار الإدارة. فشل تهيئة الجدول أو قراءته يمنع العمليات المحمية. يلزم إدراج صلاحية إنشاء الجدول ضمن مراجعة النشر، واختبار سياسات المؤسسة؛ لم يُطبق تغيير مخطط على أي قاعدة نشر أثناء تجهيز الإصلاح.
