# فحص توافق الترحيلات وإصلاح بنية القاعدة

**التحديث الحالي:** أداة الترحيل أصبحت تفحص البنية وتعيد الفهارس والمفاتيح المفقودة
وتعالج وصف المرفقات المستعادة أيضًا. دليل التشغيل التلقائي والاختبارات:
[`../deployment/database/README_AR.md`](../deployment/database/README_AR.md).
نتيجة البناء الحالي في `../dist/workspace-db-migrate.verification.json`.
الأقسام المؤرخة أدناه تحفظ تفاصيل التحقق السابق.

حزمة Go مستقلة داخل `workspace-enterprise` لفحص هوية الترحيلات قبل تجربة
الترقية. `CheckDatabase` يقرأ الكتالوج والتاريخ في transaction للقراءة فقط.
لا توجد تعديلات في الكور. فحص التاريخ والبنية الكامل لا يُستدعى تلقائيًا؛
بدءًا من 17 أكتوبر 2026 تستدعي تهيئة Enterprise في `../main.go`
إصلاح `licenses.id` بعد إنشاء مخزن SQL وقبل إتاحة الواجهات، بعد إعادة بناء الخادم.

## الملفات

- `history.go`: قراءة هويات الترحيلات والتحقق من تطابق أرقامها وأسمائها.
- `database.go`: قراءة تاريخ الترحيلات من PostgreSQL والتحقق منه.
- `history_test.go`: اختبارات مطابقة التاريخ وكشف التعارضات.
- `license_id.go`: إصلاح قيد `licenses.id` في معاملة مستقلة قابلة للتكرار.
- `license_id_test.go`: اختبار الإصلاح على PostgreSQL حقيقي معزول.
- `property_field_uniqueness.go`: استبدال قيد الحقول المستعاد `(groupid,name)`
  بفهرسي الكور اللذين يراعيان نوع الحقل ونطاقه، عند بدء Enterprise.
- `property_field_uniqueness_test.go`: إعادة إنتاج تعارض القالب وحقل النظام
  واختبار الإصلاح والحفاظ على البيانات والتراجع عند التعارض.
- `property_value_uniqueness.go`: استعادة فهرس التعارض لقيم الخصائص النشطة
  عند بدء Enterprise لمعالجة `42P10` في حفظ قيم التحكم بالوصول.
- `property_value_uniqueness_test.go`: اختبار استعلام upsert الفعلي من حيث
  هدف التعارض، وحفظ البيانات والمؤرشفات ورفض التعارضات على PostgreSQL معزول.
- `public_channel_id.go`: استعادة قيد `publicchannels.id` الذي يحتاجه حفظ
  القنوات العامة، تلقائيًا عند بدء Enterprise.
- `public_channel_id_test.go`: إعادة إنتاج فشل تعديل القناة واختبار نجاح
  المعاملة بعد الإصلاح وحفظ القنوات والرسائل والعضويات.
- `temporary_post_id.go`: استعادة قيد `temporaryposts.postid` المطلوب لحفظ
  الرسائل المؤقتة تلقائيًا عند بدء Enterprise.
- `temporary_post_id_test.go`: اختبار تراجع الحفظ قبل الإصلاح ونجاحه بعده،
  مع حفظ المحتوى والمرفقات والانتهاء وإيصالات القراءة.
- `../cmd/workspace-db-migrate/main.go`: تطبيق الترحيلات ثم فحص قيد الترخيص،
  والبنية ووصف المرفقات، أو إصلاح قيد الترخيص وحده بخيار مخصص.
- `../cmd/migration-rehearsal/main.go`: تشغيل migrator الكور على نسخة محلية معزولة.

## التجربة والاختبارات

بعد تجهيز نسخة محلية عبر Unix socket باسم يبدأ بـ `mm_upgrade_rehearsal_`،
وضبط متغيرات اتصال PostgreSQL `PGHOST` و`PGPORT` و`PGUSER` و`PGDATABASE`:


```bash
go test ./database_migration ./cmd/migration-rehearsal
```

## إصلاح حفظ الترخيص: الخطأ 42P10

استعلام الخادم `INSERT INTO Licenses ... ON CONFLICT (Id) DO NOTHING` يحتاج
فهرسًا فريدًا صالحًا على `id`. الترحيل الأصلي رقم 19 ينشئ المفتاح الأساسي
عند إنشاء الجدول؛ إذا كان الترحيل مسجلًا بالفعل والجدول فقد قيوده أثناء نقل
قديم، فلن يعيد تشغيل الخادم هذا الترحيل تلقائيًا.

الإصلاح الإضافي يستعلم عن الجدول الذي يحله `search_path` لاتصال الخادم، ثم
يحجز الكتابات خلال الفحص والإصلاح. ينتظر القفل 5 ثوانٍ كحد أقصى، ولكل
استعلام حد 30 ثانية. يفحص التكرارات والقيم NULL ويرفضها دون تعديل السجلات.
إذا وجد مفتاحًا أو فهرسًا فريدًا مناسبًا، لا يغير شيئًا. وإلا يعيد إنشاء
`PRIMARY KEY (id)`، أو يضيف `UNIQUE (id)` إذا كان هناك مفتاح أساسي آخر.
لا يزيل القيود أو الفهارس الموجودة، ولا يبدل بيانات الترخيص أو يصدر ترخيصًا.
القيود المؤجلة `DEFERRABLE` تحتاج مراجعة منفصلة، وليست هدفًا صالحًا لهذا
الاستخدام من `ON CONFLICT`.

من `mattermost/server`، بعد أخذ نسخة احتياطية للقاعدة المستهدفة، لتطبيق
إصلاح الترخيص وحده باستخدام **ملف إعدادات القاعدة التي تريد إصلاحها**:

```bash
go run ../../workspace-enterprise/cmd/workspace-db-migrate \
  -config /absolute/path/to/config.json \
  -repair-license-id-only
```

هذا أمر يكتب إلى القاعدة المحددة؛ الأداة لا تأخذ نسخة احتياطية بنفسها.
خيار `-repair-license-id-only` لا يشغّل ترحيلات الكور ولا يغير تاريخها.
الأمر العادي `workspace-db-migrate` يشغّل الإصلاح بعد نجاح ترحيلات الكور،
حتى عندما لا توجد ترحيلات جديدة. بعد إعادة البناء، تشغيل `mattermost`
مع Enterprise يستدعي إصلاح قيد الترخيص تلقائيًا بمهلة كلية 35 ثانية،
ويسجل الفشل دون تعديل السجلات المتعارضة. توجد إصلاحات تلقائية إضافية موثقة
في `../cmd/workspace-db-migrate/README.md`؛ فحص البنية الكامل يتطلب أداة
الترحيل قبل الخدمة ضمن خطوات النشر.

لبناء أداة مستقلة قابلة للنقل:

```bash
go build -o ../../workspace-enterprise/dist/workspace-db-migrate \
  ../../workspace-enterprise/cmd/workspace-db-migrate
```

الأداة في مسار Enterprise فقط ولا تحتاج تعديل مصدر `server` أو تغيير
`db_migrations` يدويًا. إعادة التشغيل بعد نجاح الإصلاح لا تعيد إضافة القيد.

### اختبار PostgreSQL حقيقي

`WORKSPACE_LICENSE_MIGRATION_TEST_DSN` يجب أن يشير إلى PostgreSQL مؤقت
على Unix socket، ومسار بياناته يبدأ بـ `/tmp/workspace-license-migration-`.
ترفض الاختبارات أي خادم آخر لحماية قواعد العمل. تنشئ schema لكل حالة
وتحذفها بعد الاختبار. عند غياب المتغير تُتجاوز اختبارات PostgreSQL فقط.

```bash
go test ./database_migration -run 'TestRepairLicenseID' -v -count=1
```

شملت التجربة على PostgreSQL 16: المفتاح المفقود، الجدول الفارغ، المفتاح
الموجود، الفهرس الفريد مع أعمدة INCLUDE، الفهرس الجزئي والمركب، مفتاح أساسي
على عمود آخر، التكرارات، NULL، القيد المؤجل، تعارض اسم القيد، والجدول المفقود.
تتحقق الحالات الناجحة من إعادة التشغيل دون تغيير ومن نجاح `ON CONFLICT`
دون إدراج نسخة أخرى، ومن تطابق سجلات الترخيص قبل الإصلاح وبعده.

## مجريشن NULL في بريد المستخدمين — 17 أكتوبر 2026

`user_email.go` يطبّق `RepairUserEmail` بمعاملة واحدة. تستخدمه تهيئة
`user_no_email.Register` المسجلة في `main.go` عند بدء المشروع. السبب المؤكد
هو فشل `GET /api/v4/reports/users` عند قراءة NULL، وفشل المجريشن السابق
عند التحويل إلى نص فارغ بسبب الفهرس الفريد الكامل `idx_users_email`.

الإصلاح يفحص فهارس البريد الفريدة من كتالوج PostgreSQL، ويحوّل الفهرس
الكامل إلى جزئي يستثني البريد الفارغ مع إبقاء الاسم والتعريف والأعمدة INCLUDE.
يحافظ على الفهارس الجزئية المناسبة، ويضيف واحدًا إذا لم يوجد. بعد ذلك
يحوّل NULL فقط إلى نص فارغ ويضبط DEFAULT وNOT NULL. تتراجع المعاملة
عند وجود بريد حقيقي مكرر أو فهرس غير صالح أو قيد مؤجل أو علاقة تعتمد على
القيد القديم؛ لا يستخدم CASCADE ولا يحذف حسابات.

`user_email_test.go` يعيد إنتاج الفشل على PostgreSQL معزول، ويختبر التكرار
وحفظ البيانات وتفرّد البريد ومنع NULL والتراجع. لم يُتصل بقاعدة العمل أثناء
هذا التعديل. تقرير التحقق:
[`../audit/2026-10-17/user-report-migration/README_AR.md`](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-17/user-report-migration/README_AR.md).

## سياسات الاحتفاظ والخطأ 42803 — 17 أكتوبر 2026

`retention_policy_id.go` يعيد المفتاح الأساسي `retentionpolicies(id)` عند
غيابه، دون تغيير السياسات أو الارتباطات أو مدد الاحتفاظ. الاستدعاء موجود
في `main.go` داخل تسجيل `DataRetentionInterface`، قبل إنشاء الخدمة.
يحترم المفتاح الصحيح حتى عند اختلاف اسمه، ويرفض المفتاح المختلف أو المؤجل
ومعرّفات السياسات المكررة أو NULL. لا يكتفي بفهرس UNIQUE لأن PostgreSQL
لا يستخدمه لإثبات الاعتماد الوظيفي المطلوب لاستعلام GROUP BY في هذا المسار.

المهلة الكلية عند البدء 35 ثانية، وحد انتظار القفل 5 ثوانٍ. تتراجع المعاملة
عند الفشل ويُسجل الخطأ. الاختبارات تعيد استعلام القائمة التجميعي وأعداد الفرق
والقنوات على PostgreSQL معزول، دون اتصال بقاعدة العمل. التقرير:
[`../audit/2026-10-17/retention-policy-migration/README_AR.md`](../../workspace-audits/workspace-enterprise-2026-10-22/audit/2026-10-17/retention-policy-migration/README_AR.md).
